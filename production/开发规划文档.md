## 一、规划原则

1. **模块化推进，后端与单元测试优先**：每个模块按「后端接口 → 单元测试通过 → 客户端 → 联调验证 → 文档更新」的顺序走。
2. **每个模块必须有可独立验证的交付物**：说不清怎么验收的模块不进计划。
3. **完成一个模块就停下**，由你确认是否进入下一个模块。
4. **数值与规则不写进代码**，全部集中在规则配置里；调数值只改配置。
5. **没有设计图的页面不动工**，绝不脑补视觉。
6. **素材先处理再使用**：现有设计图全部是 JPG 假透明，抠图是独立的前置任务。
7. **文档随代码走**：任何新增/修改/删除都要同步更新对应文档，不留无文档的代码改动。

  - 校验规则（新增）：**客流上限二态校验**（GDD `§5.7`）——`capFrozen == false` ⇒ `dailyVisitorCap` 必须 `== 0`（占位，读取方忽略）；`capFrozen == true` ⇒ 必须落在合法档位集合 `{baseVisitors + visitorsPerShop × k | k ∈ [1,5]}`。**不得**用 `dailyVisitorCap` 的取值反推冻结状态
  - 单元测试：正常路径 + 边界（金币不足、跳过解锁顺序、重复解锁幂等、满级再升级、对「待开业」店铺升级被拒、解锁后当日客流不变、单价变化时账单分段正确、**空段（`visitors == 0`）语义**、**开店建立首个分段（含触发满铺时只产生一条 bonus 段）**、**`unlockedSlots` 加载校验（未知/跳序/重复/越界）**、**并发解锁/升级只提交一次**、**消费后存档仍能通过自证**）
- **验收标准**（每条含**前置条件**，便于直接转成测试用例）：
  1. **前置**：某二层铺位处于「未开放」，且金币不足其 `unlockCost`。**期望**：解锁失败返回 `INSUFFICIENT_COINS`，金币与存档零变化。
  2. **前置**：衣橱（`unlockOrder=1`）仍处于「未开放」。**期望**：直接解锁甜屋（`unlockOrder=2`）被拒绝（`SLOT_ORDER`），零变化。**加载校验**：存档 `unlockedSlots` 含未知 `slotId` / 跳序（缺 `unlockOrder=n-1`）/ 重复项 / 数量越界，均判定为存档损坏并拒绝加载（见 GDD `§3.7` / `§5.5`）。
  3. **前置**：某铺位已解锁。**期望**：重复解锁为**幂等成功**（`changed=false`），不重复扣费、不写存档。
  4. **前置**：店铺处于「营业中」且当日已产生客流。**期望**：升级后新产生的收益按新等级单价记账，历史账单不被改写，且每一段 `revenue == visitors × unitPrice` 成立（**含 `visitors == 0` 的空段**）。
     - **开店建段（新增）**：**前置**：店铺处于「待开业」。**期望**：开店（`prepare`）时建立**首个分段**，其 `unitPrice` 取重算满铺后的值；`prepare` 的硬顺序为「置 `prepared` → 重算满铺 → 建/append 段」，**不得调换**。若该店恰好触发所在层满铺，则它**只产生一条 bonus 价段**（`unitPrice = 等级单价 + 满铺加成`），**不得**出现 spurious 的 pre-bonus 空段；同层其他已开业店各 append 一条新段。
  5. **前置**：当日尚未产生任何客人（`openShopCount == 0`）。**期望**：当日上限**不冻结、不落盘**；在首次实际产生客人的结算（`openShopCount ≥ 1`）时才冻结为 `dailyVisitorCap`；冻结后中途再开店不改变当日上限，次日生效。
     - **「未冻结」的判定依据（GDD `§5.7`）**：以 `capFrozen`（bool）为**唯一判据**。`capFrozen == false` ⇒ 存档 `dailyVisitorCap` 落盘占位 `== 0`、接口返回 `null`、HUD 显示占位 `— / —` 且**不显示分母**；`capFrozen == true` ⇒ 值落合法档位集合 `{baseVisitors + visitorsPerShop × k | k ∈ [1,5]}`，HUD 显示 `已到店 / 上限`。**不得**用 `0` 作哨兵、不得用 `dailyVisitorCap` 的取值反推冻结状态。
  6. **前置**：某层至少有一个铺位处于「未开放」或「待开业」。**期望**：该层满铺加成不生效（0）；当该层全部铺位处于「营业中」时加成生效（+1）。
  7. **前置**：某铺位处于「未开放」。**期望**：其累计客流与累计收益恒为 0（该不变量在解锁前后均须成立）。
  8. **前置**：店铺处于「待开业」。**期望**：升级被拒绝返回 `SHOP_NOT_OPEN`，且状态零变化。
  9. **并发**：
     a. **并发解锁同一铺位**：只提交一次、只扣一次费；另一请求为幂等成功或明确拒绝。
     b. **并发升级同一店铺**：只提交一次、只扣一次费。
     c. **并发解锁与升级**：两笔互不干扰、各自正确扣费，`coins` 与 `spent` 守恒。
     d. 解锁与升级必须与 `prepare` 共用同一套互斥锁与"先落盘再发布"语义。
  10. **消费后存档仍能自证**：解锁/升级使 `coins < initialCoins` 之后，存档仍被正常加载（下界为 `coins >= 0`）。
  11. `gofmt` / `go vet` / `go test -race` 全绿。
- **风险**：存档 schema 变更会让旧存档被拒绝加载（预期行为）；开发期直接删档。

- **风险**：客人走位与轮询节奏不同步会出现"看到客人却没有收益"的错觉，需要把表现对齐到服务端返回的到店数。
