## 1. 微信小游戏平台事实

### 1.1 包体积上限 —— 主包 4MB（✅ 正确）/ 总包 30MB（美术假设偏保守）

**官方现行文档**《分包加载》（`developers.weixin.qq.com/minigame/dev/guide/base-ability/subPackage/useSubPackage`）原文：

> 目前小游戏分包大小有以下限制：
> - 整个小游戏所有主包+分包大小不超过 **30M**
> - 主包不超过 **4M**
> - 单个普通分包不限制大小
> - 单个独立分包不超过 4M

**判定：**

- 美术假设「主包 ≈ 4MB」—— ✅ **正确**，且是硬上限（不是估算）。
- 美术假设「总包 ≈ 20MB」—— ⚠️ **偏保守**：官方现行为 **30MB**，实际可用空间比假设**多 10MB**。美术"按比例缩放预算"的做法安全，结论（首包省、分包放）不变，且更宽松。

**⚠️ 版本漂移提示（必须知道，避免被旧资料误导）：**

| 数值 | 出处 | 状态 |
| --- | --- | --- |
| 30M 总 / 4M 主 | 官方现行文档（本次核对） | **以这个为准** |
| 8M 总（"所有分包不超过 8M"） | 微信社区旧帖（6.6.0 时代） | **已过期** |
| 20M 总（"开通虚拟支付后 30M"） | 第三方 gitee 实践文档 | 非官方，与现行官方文档冲突 |

**行动**：提审前再复核一次官方文档数值（列入 §3 清单）。

#### 1.1.1.0 前置：先分清「源文件体积」与「运行时体积」

> **这一条不写清，后面全部算错。**

| 概念 | 是什么 | 由什么决定体积 | 是否进包 |
| --- | --- | --- | --- |
| **源文件体积** | 美术交付的 `NewProject/assets/textures/` 下**无损 PNG** 文件 | 像素尺寸 + 无损压缩率 | **否**（源文件是制作中间物，不随包分发）<br>⚠️ **此「否」仅指「可编辑源文件」本身**——由它**派生的「默认图 / fallback」是构建产物，随包且计入主包**，见 **§1.1.2** / 《美术圣经》§5.5.1 |
| **运行时体积** | 构建时由源图生成的**压缩纹理**（ASTC / ETC2）**及通用格式默认图**（PNG/JPG） | ⌈宽÷块⌉ × ⌈高÷块⌉ × 每块字节；默认图另按通用压缩率 | **是**（真正占包体的是这个） |

- **实测（2026-09-14 · 本仓库）**：`NewProject/assets/textures/` 现有 **20 张无损 PNG 源文件，合计 4,524,943 B = 4.315 MiB**（逐文件清单见本节末附表）。**此数不能直接与主包 4MB 相比**——它是**源文件**，不进包。
- **运行时换算（估算）**：同样这 20 张若统一转 ASTC，运行时合计约 **2.42 MiB（6×6）/ 1.35 MiB（8×8）**，仅为源文件体积的 **约 1/1.8 ~ 1/3.2**。
- **引擎不占主包（官方明文旁证）**：Cocos 引擎自微信 **7.0.7** 起作为**内置插件**随微信客户端提供，**引擎代码不计入主包 4MB**（依据本文件 §2.2 已核对结论）。→ **反推预算时不需要给引擎留体积。**

> ⚠️ **给美术侧的第一句话**：做预算时**一律按「运行时压缩纹理」形态算，不要按源 PNG 体积算**。§5.3 的 KB 目标若指的是源 PNG，那它与 §5.4「PNG-24+alpha 无损」就是**同一件事的两种说法**，必然对不上（实测无损 512×640 立绘 = **275 KiB**）。

> ### ✅ 2026-09-19 复核结案：引擎**计入**主包，「不占主包」结论作废
>
> **官方明文**（Cocos Creator 3.8《微信小游戏引擎插件使用说明》FAQ，逐字）：
>
> > Q：启用引擎插件后，是否仍然会把引擎代码算入首包包体中？
> > A：根据微信的规则，目前仍然会计算在内。
>
> 同页另两条与本节直接相关：**「引擎插件提供的是完整版引擎……不会影响原有项目的包体」**——启用引擎插件／引擎分离**不会**让包变小；**「项目可以按原来的方式继续裁剪引擎」**——真正能减包的是**功能裁剪**（项目设置 → 功能裁剪，落在 `NewProject/settings/v2/packages/engine.json`）。

#### 1.1.1.1 可用预算的量级推导

**（A）主包 4 MiB 里，美术素材可用多少？**

主包上限 = **4 MiB = 4,096 KiB**（**官方明文**，§1.1）。扣除非美术项（**估算**，假设逐项列出）：

| 扣除项 | 量级 | 依据 / 假设 |
| --- | --- | --- |
| 引擎运行时 | **实测 1443 KiB（功能裁剪后；裁剪前 2541 KiB）** | ⚠️ **2026-09-19 结案：原记「0，不占主包」为错误**——官方 FAQ 明文「启用引擎插件后……目前仍然会计算在内」，且原引 §2.2 属引用错位。减包手段是功能裁剪而非引擎插件，详见本节末 ✅ 块 |
| 游戏代码 + 首屏逻辑（JS / 编译产物） | ~~估算 300–600 KiB~~ | ⚠️ 原为估算，**已被下面的实测整体取代**（勿与实测重复相加） |
| 配置 / 场景 / 元数据（JSON 等） | ~~估算 ≤ 100 KiB~~ | 同上，已并入实测 |
| 平台必需（app 图标 / manifest 等） | ~~估算 ≤ 100 KiB~~ | 同上，已并入实测 |
| **非美术小计** | **实测 1,786.5 KiB** | **实测（2026-09-19）**：`tools/m04_build.py` 对构建产物逐文件加总。构成＝引擎 1,443.0 + `assets/internal` 等 158.4 + `src` 26.8 + 根部 js/png 158.3。**其中不含任何一张游戏素材**——占位图未被场景引用，不进包 |

→ **主包美术可用 ≈ 4,096 − 1,786.5 ≈ 2,310 KiB ≈ 2.26 MiB**。

> ⚠️ **本行原写「≈ 3.5 MiB」，系建立在「引擎不占主包」这一已被推翻的前提上**（见本节末 ✅ 块）。
> 与《美术圣经》§5.3.0 的首包素材预算 **≤ 2.27 MiB** 对照：**刚好放得下，余量约 0 KiB**，且**尚未计入 M04 之后新增的 TS 代码**（原估 300–600 KiB 那部分一旦落地，主包必然超）。
> **结论：素材分包／远程包由「优化项」升级为「必做项」**——不能指望把 13 件素材全塞进主包。这条要回改到《美术圣经》§5.3.0 与《开发规划文档》M04 交付物里。

**（B）总包 30 MiB 里，美术素材总量预算是多少量级？**

总包上限 = **30 MiB = 30,720 KiB**（**官方明文**，§1.1）。扣除项（**估算**）：

| 扣除项 | 量级 |
| --- | --- |
| 主包（含代码 + 首包美术，即上面 4 MiB） | 4 MiB |
| 音频（BGM + 音效，属阮和鸣范围） | 估算 **2–5 MiB** |
| 后续分包代码 / 数据 | 估算 **≤ 1 MiB** |
| **非美术小计** | **估算 ≈ 7–10 MiB** |

→ **美术总量预算 ≈ 30 −（7~10）≈ 20–23 MiB**，**量级 ≈ 20 MiB**。

> **与美术侧现状对照（这是本节最有用的一句话）**：《美术圣经》§5.5 自设「全量美术 **≤ 3.98 MiB**（首包 1.53 + 分包 2.45）」。→ **美术侧的自设预算远严于平台上限**：总量只用到可用量级的约 **1/5**，首包只用到约 **1/2.3**。**结论：包体上限对美术侧不构成压力；需要纪律的是「单张别定错尺寸」，不是「省总量」。**

**（C）「首包放什么 / 分包放什么」的分界建议**

沿用《美术圣经》§5.2 的既有结论（「首包省、分包放」），分界线一句话：

- **进首包** = **首屏一帧内必须出现、首屏就要用的**：`bg_mall_base`（全屏背景）、`atlas_hud`（HUD）、`atlas_state`（状态叠加）、`font_*_subset`（字体子集）、`app_*`（图标 / 启动图）。
- **进分包** = **需交互 / 切换后才出现的**：`atlas_slot`（空铺底图）、`atlas_shop_2f` / `atlas_shop_1f`（店铺立绘）、`atlas_guest`（客人）、`atlas_props`（装饰）、`ui_card_postcard`（明信片）。
- **判据**：**「首屏看不见的，就别进首包」**。**5 张店铺立绘一律进分包**（与 §5.5 纪律 2 一致）。

#### 1.1.1.2 折算到单张资产的目标区间

> **算式（可复现）**：`压缩纹理体积 = ⌈宽 ÷ 块边长⌉ × ⌈高 ÷ 块边长⌉ × 16 B`。
> 其中 **16 B/块** 是 **ASTC 的固定块字节数**（ASTC LDR 每块恒为 **128 bit**，与块尺寸无关）——来源见 §4 #11（**ASTC 格式规范 · Khronos**）。**这是格式常量，不是微信平台规则。**
> 「无损 PNG」列 = **实测**（本仓库现有源文件）；「ASTC」列 = **估算**（按上式，**未含 mipmap**；若开 mipmap 约 +33%）。

| 资产 | 出图尺寸 | 无损 PNG（**实测**） | **ASTC 6×6**（含 alpha 推荐档，**估算**） | **ASTC 8×8**（无 alpha 背景推荐档，**估算**） |
| --- | --- | --- | --- | --- |
| **店铺立绘** `shop_*_open` | 512×640 | **256–325 KiB**（实测 3 张：256 / 275 / 324） | **≈ 143.8 KiB**（86×107×16） | **≈ 80.0 KiB**（64×80×16） |
| **空铺底图（2F）** `slt_f2_empty` | 512×640 | **242 KiB**（实测） | **≈ 143.8 KiB** | **≈ 80.0 KiB** |
| **空铺底图（1F）** `slt_f1_empty` | 704×1024 | **478 KiB**（实测） | **≈ 315.3 KiB**（118×171×16） | **≈ 176.0 KiB**（88×128×16） |
| **主界面背景** `bg_mall_base` | 1125×2000 | 未制作；按现有大图实测 **0.6–0.7 B/px** 推算 **≈ 1.4–1.5 MiB**（**估算**） | **≈ 981.1 KiB**（188×334×16） | **≈ 550.8 KiB**（141×250×16） |
| **5 槽 HUD 底板** `ui_hud_bar` | 1024×256 | **299 KiB**（实测） | **≈ 114.9 KiB**（171×43×16） | **≈ 64.0 KiB**（128×32×16） |

（对照：`ui_panel_wood` 512×512 → ASTC 6×6 **≈ 115.6 KiB** / 8×8 **= 64.0 KiB**。）

> **读法**：立绘带 alpha → 按官方推荐走 **ASTC 6×6**，单张 **≈ 144 KiB**；背景无 alpha → 走 **ASTC 8×8**，单张 **≈ 551 KiB**（若背景也必须带 alpha，则按 6×6 **≈ 981 KiB**）。

#### 1.1.1.3 直接回答：《美术圣经》§5.3 的 `≤70KB` 在哪种形态下才成立？

**结论：在 512×640 这个尺寸上，`≤70KB` 在任何「官方推荐的形态」下都不成立。**

逐形态核对（512×640 立绘）：

| 形态 | 体积 | 对 `≤70KB` 的判定 |
| --- | --- | --- |
| 无损 PNG-24+alpha（§5.4 要求） | 实测 **275 KiB**（区间 256–325 KiB） | ❌ **超约 3.9×** |
| ASTC 6×6（官方 alpha 推荐档） | **143.8 KiB** | ❌ **超约 2.1×** |
| ASTC 8×8（官方背景推荐档） | **80.0 KiB** | ❌ **仍超约 14%** |
| ASTC 10×10 | 52.0 KiB | ✅ 落入 70KB，但**非**官方对「含 alpha 贴图」的推荐档（官方 alpha 推荐 4×4 / 5×5 / 6×6） |

**根因**：`≤70KB` 这个数是在**不知道包体上限**的前提下、按「源文件形态」拍出来的（用户已裁定）。它同时**低于**「无损源文件」（275 KiB）**和**「官方推荐的运行时压缩形态」（6×6 = 143.8 KiB、8×8 = 80 KiB）——所以在**两种形态里都对不上**：无损下超 3.9 倍，压缩下超 2.1 倍，**连最省的一档（8×8）都还差 14%**。

#### 1.1.1.4 对《美术圣经》§5.3 的明确建议（**由美术侧自行落，本节不改其文件**）

**建议一（首选 · 改计量形态 + 改量级）**：把体积目标的**计量形态**从「源文件」改成「**运行时压缩纹理**」，并按官方推荐档给量级：

- **表述改为**：**「体积目标 = 运行时压缩纹理（ASTC）形态；源 PNG 无损文件只约束像素尺寸，不设 KB 上限。」**
- **量级（运行时 ASTC）**：
  - 含 alpha 资产（立绘 / 底图 / 状态件）→ 按 **ASTC 6×6**：512×640 **≈ 144 KiB**，建议目标 **≤ 160 KiB/张**（留余量）。
  - 无 alpha 资产（主背景）→ 按 **ASTC 8×8**：1125×2000 **≈ 551 KiB**，建议目标 **≤ 600 KiB**。
- **理由**：这样目标才与 §5.4「运行时用 ASTC 6×6 / 8×8」**同一口径**，§5.3 与 §5.4 的矛盾自然消解。

**建议二（若美术侧坚持保留「源文件 KB 目标」）**：那就必须承认**源文件与运行时是两套数**，并把 §5.3 的 KB 值改到**源文件形态的真实量级**——512×640 无损源 PNG 实测 **≈ 275 KiB**（3 张实测 256–325 KiB），建议目标定 **≤ 350 KiB/张（源文件）**，并明确「**此值不用于包体核算；包体按运行时 ASTC 核算**」。

**不建议**：为凑 `≤70KB` 而降块到 ASTC 10×10 / 12×12 或降分辨率——那会偏离官方对含 alpha 贴图的推荐档（6×6），**用画质换一个本就不必要的数字**。

> **一句话给美术侧**：`≤70KB` 应**改成按运行时压缩纹理（ASTC 6×6）定目标**——立绘量级 **≈ 144 KiB（目标 ≤ 160 KiB）**、背景（ASTC 8×8）**≈ 551 KiB（目标 ≤ 600 KiB）**；**源 PNG 无损文件不设体积目标，只设像素尺寸**。

### 1.1.2 「默认图 / fallback」是否随包 —— 三项核对（SC-ARCH-007）

> **本节定位**：SC-ARCH-007 的交付——核实 **Cocos Creator 3.8.8 发布微信小游戏时，纹理压缩预设的「默认图 / fallback」是否随包分发、其体积是否计入主包 4MB、能否指定降规格版本**，用于判定《美术圣经》§5.5「默认图三情形」该走 **A** 还是 **C**。
> **核对日期**：2026-09-14（沿用本文件 §1.1 已核对的包体上限；本轮新增来源见 §4 #12–#14）
> **术语澄清（重要，先分清再判定）**：**Cocos 的「默认图」** = 在**压缩纹理预设**里额外添加的**通用图片格式（PNG/JPG）**，构建时与 ASTC 等压缩格式**一起生成**，供引擎在**不支持压缩格式的设备**上兜底加载。它 **≠ 微信平台层面的任何概念**，也 **≠ 源工程内的原始资产（可编辑源文件）**。
> **标注口径**：沿用本文件——「**官方明文**」= 官方文档逐字表述；「**工程判断**」= 由官方明文推导、但官方**未逐字点名**。

#### 1.1.2.0 三项核对结论速览

| # | 问题 | 判定 | 档位 |
| --- | --- | --- | --- |
| **Q1** | 默认图 / fallback 是否**随包分发** | ✅ **是（随包分发）** | **官方明文** |
| **Q2** | 默认图体积是否**计入主包 4MB** | ✅ **计入**（该纹理属主包时） | **官方明文（旁证充分，非逐字点名）** |
| **Q3** | 能否指定**降规格**版本作默认图 | ⚠️ **部分可以**：转 JPEG ✅ / 低质量 ✅ / **半分辨率 ❌（预设无此选项）** | Q3a·Q3b **官方明文**；Q3c「无选项」**官方明文**、替代路径**工程判断** |

> **一句话结论**：**默认图随包、计入主包**——故《美术圣经》§5.5.1 的判断「**默认图几乎肯定是随包分发的构建产物**」**成立**，§1.1.1 的「源文件不进包」**只说对了一半**（*可编辑源文件*不进包，**由它派生的默认图进包**）。→ **§5.5 应走情形 C**（见 1.1.2.4）。

#### 1.1.2.1 Q1 — 默认图 / fallback 是否随包分发？→ ✅ **是**（官方明文）

**Cocos 官方《压缩纹理》**（`https://docs.cocos.com/creator/3.8/manual/zh/asset/compress-texture.html`）逐字：

> - "支持同一平台**同时导出多种图片格式**，引擎将根据设备对压缩纹理格式的支持情况加载合适的压缩纹理。"
> - "**注意**：配置了压缩纹理后，**只有对应格式的图片会在构建时生成**，若有些图片格式在部分设备上不支持就会导致显示异常。为避免该问题，在添加纹理压缩预设时，请**额外选择一些通用图片格式（例如 PNG、JPG）作为默认图**。"
> - "这些**生成的图片**不会都被加载到引擎中，引擎会根据 `macro.SUPPORT_TEXTURE_FORMATS` 中的配置来选择加载合适格式的图片。……引擎加载图片时会从**生成的图片**中找到在这个列表中优先级靠前的格式来加载。"

**推导链（官方明文 → 结论，可复现）**：

1. 「默认图」是**构建时生成**的图片格式之一（与 ASTC 并列，同一张纹理同时导出多种格式）；
2. 这些**生成的图片位于构建产物（发布包）**中——否则引擎运行时无从「从生成的图片中」按优先级挑选加载；
3. 设备要能用它 fallback，**该文件必须实际存在于设备上** → **它随包分发**。

**微信侧旁证**（`https://developers.weixin.qq.com/minigame/dev/guide/base-ability/code-package.html` · 《代码包》·「文件类型」）逐字：

> "在项目目录中，以下文件会经过编译……除此之外，**只有后缀名在白名单内的文件可以被上传**，不在白名单列表内文件在开发工具能被访问到，但无法被上传。"

白名单**含** `png / jpg / jpeg / astc / ktx / pkm` 等 → **包内容 = 项目目录（构建产物）中白名单文件**，图片文件在上传之列。

**结论**：✅ **默认图随包分发**（**官方明文**）。它**不是**「仅存在于源工程内的原始资产」——§5.5.1 的「字面理解」正确。

#### 1.1.2.2 Q2 — 默认图体积是否计入主包 4MB？→ ✅ **计入**（官方明文，旁证充分）

**微信官方《代码包》**逐字：

> "代码包总大小不能超过 **30M**，单个分包不限制大小，**主包不超过 4M**。"

**Cocos 官方《发布到微信小游戏》**（`https://docs.cocos.com/creator/3.8/manual/zh/editor/publish/publish-wechatgame.html`）逐字：

> "小游戏的主包体积**不能超过 4MB，包含所有代码和资源**，额外的资源必须通过网络请求下载。"

**判定口径**：

- 包体上限是**对「包内容」整体计**的，而包内容 = 构建产物中的白名单文件（Q1 已证）；
- 默认图是构建产物中的**图片资源** → **计入其所属包**：纹理在**主包** → 默认图计入 **主包 4MB**；纹理在**分包** → 计入 **总包 30MB**。
- ⚠️ **诚实标注**：官方文档**未逐字点名**「默认图计入主包 4MB」这一句；本节结论由「**主包包含所有代码和资源**」（官方明文）+「**包 = 构建产物白名单文件**」（官方明文）**推导**而来，档位记为「**官方明文（旁证充分）**」，非逐字明文。

**结论**：✅ **计入主包 4MB（该纹理属主包时）。** 对本项目——**主包内的默认图直接吃掉 4MB 预算**，这正是《美术圣经》§5.5.1 情形 B「爆包」的机制。

#### 1.1.2.3 Q3 — 能否指定降规格版本作默认图？→ ⚠️ **部分可以**

**Cocos 官方《项目设置 · 压缩纹理》**（`https://docs.cocos.com/creator/3.8/manual/zh/editor/project/index.html`）逐字：

> - "选择平台，然后点击 **Add Format** 按钮，**选择需要的纹理格式，再配置好对应的质量等级即可**，目前同类型的图片格式只能添加一次。"
> - 可用格式类型 `ITextureCompressType`（19 种）：`jpg | png | webp | pvrtc_4bits_rgb | … | etc1_rgb | etc2_rgb | etc2_rgba | astc_4x4 | astc_5x5 | astc_6x6 | astc_8x8 | astc_10x5 | astc_10x10 | astc_12x12`
> - 质量等级（官方示例值）：`"fast"`、`"-medium"`——**按「格式 × 平台」分别配置**，无全局默认质量入口。
> - Mipmap：`Mipmaps for compressed textures`（`Allow Pre-generation` / `Disabled`）——"开启后**生成多张图片，会影响到包大小**"。

| 子项 | 能否 | 依据 | 档位 |
| --- | --- | --- | --- |
| **Q3a · 转 JPEG 作默认图** | ✅ **可以** | 预设格式列表含 `jpg`；官方原话即"通用图片格式（**例如 PNG、JPG**）作为默认图" | **官方明文** |
| **Q3b · 用低质量版本** | ✅ **可以** | 预设支持"配置对应的**质量等级**"（示例 `fast` / `-medium`） | **官方明文** |
| **Q3c · 用半分辨率** | ❌ **预设无此选项** | 项目设置「压缩纹理」面板**无任何「分辨率 / resolution / scale」选项**（该面板只提供 **格式 + 质量 + mipmap**）；自定义任务结构 `ICompressTasks` 亦**无** scale/width/height 字段 | 「无选项」**官方明文** |

> ⚠️ **JPEG 无 alpha**：JPEG **不支持透明通道**，故**含 alpha 的资产不能把默认图设为 JPEG**，只能用 PNG；**无 alpha 的背景**才可用 JPEG 换取大幅体积下降。

**Q3c 的替代路径（⚠️ 工程判断，非官方明文）**：Cocos 提供**官方「自定义纹理压缩」机制**（`https://docs.cocos.com/creator/3.8/manual/zh/editor/publish/custom-build-plugin.html`）：

> `src/builder.ts`：`export const assetHandlers = './asset-handlers';`
> `src/asset-handlers.ts`：`export const compressTextures: AssetHandlers.compressTextures = async (tasks) => {…}`
> 任务结构含 `src`（源文件地址）/ `dest`（**生成的目标文件地址**，后缀默认 PNG）/ `quality`（**压缩质量 0–100 或压缩等级**）/ `format`（压缩类型）。
> "处理函数会接收当前剩余的未被处理的纹理压缩任务数组，处理完成后从原数组中移除。"

→ **可在插件里对「默认图格式」的任务自行做缩放**（读 `src` → 缩到半分辨率 → 写 `dest`）。**注意**：官方**未**内置 scale 参数，"缩放"须插件内自行用图像库实现——**属工程判断，非官方明文**。

**结论**：Q3 **部分可以**——**转 JPEG / 降质量 = 官方明文可配；降分辨率 = 预设不支持，需自定义构建插件（或另出半分辨率源资产）**。

#### 1.1.2.4 最终判定：§5.5 走 **情形 C**

| 情形 | 是否可行 | 判定理由 |
| --- | --- | --- |
| **A · 不做默认图** | ⚠️ 可行但**不满足 §5.4 🔴 硬约束** | Cocos 官方**明确要求**保留通用格式作默认图（否则不支持压缩格式的设备显示异常）；放弃它 = 主动违背官方明示 + §5.4 |
| **B · 原尺寸无损 PNG 进包** | ❌ **不可行** | 默认图**确实随包、计入主包**（Q1/Q2 已证）→ 主包被顶爆（§5.5.1 实测 ≈5.52 MiB > 4MB） |
| **C · 降规格默认图进包** | ✅ **可行（推荐）** | 既满足 §5.4「有保底」，又落在 4MB 内（§5.5.1 估 ≈3.53 MiB，余 ≈0.5 MiB） |

**判定：走情形 C。** 理由：

1. **Q1/Q2 证实默认图随包且计入主包** → 情形 B 的字面执行结果**必然爆包**，且**不存在「默认图不进包」的官方空间**可退（故 A 不能以"官方默认做法"自居）。
2. **§5.4 是 🔴 硬约束、且与 Cocos 官方要求一致** → **不应走 A**（放弃保底 = 违背官方明示，且会让**微信开发者工具**预览时显示异常——Cocos 明确注明"开发者工具不支持 ASTC，需真机调试"）。
3. **C 在预算内** → §5.5.1 已算 ≈3.53 MiB（含 ≈600 KiB 代码），主包余 ≈0.5 MiB，**可行**。

> **与美术侧判断一致**：美术侧（《美术圣经》§5.5.1）判定「默认图几乎肯定是随包分发的构建产物」「推荐落点 C」——**本次核对证实其判断成立**。

#### 1.1.2.5 本项目的建议配置（走 C 的具体做法）

**① 预设设计（按 alpha 分流，两套预设；此步零代码）**

| 预设 | 适用资产（首包） | MiniGame 平台格式 | 默认图（fallback） |
| --- | --- | --- | --- |
| `main_noAlpha` | `bg_mall_base`（无 alpha 背景） | `astc_8x8`（medium） | **`jpg`（低质量档）** |
| `main_alpha` | `atlas_hud` / `atlas_state` / `app_*`（含 alpha） | `astc_6x6`（medium） | **`png`（最低质量档）** |

**操作**：**项目设置 → 压缩纹理 → Add Format**（分别选 `jpg` / `png` 并配质量档）→ 在图片资源属性检查器勾 `useCompressTexture` 并选对应 `presetId`。
（依据：官方《项目设置》"选择平台 → Add Format → 选择格式 → 配置质量等级"；§1.1.2.3。）

**② 降分辨率（仅当 ① 后仍超预算才启用；需自定义构建插件）**

- `src/builder.ts`：`export const assetHandlers = './asset-handlers';`
- `src/asset-handlers.ts`：`compressTextures(tasks)` 中，对 `task.format === 'jpg' | 'png'`（即默认图任务）且 `task.src` 属**首包路径**者，**将源图缩放到 1/2 边长**后写入 `task.dest`；处理完从 `tasks` 移除（否则会回落到 Cocos 原有流程）。
- 依据：官方《自定义纹理压缩处理》——`ICompressTasks` 的 `dest` / `quality` / `format` 可控；"处理完的纹理压缩任务，将其从 tasks 里移除"。**缩放逻辑本身为工程判断（官方无内置 scale 参数）。**

**③ 预算纪律（不变）**：源工程**仍保留全分辨率无损 PNG**（用于生成 ASTC）；**只对默认图降规格**；默认图**只对进首包的资产出**，分包资产的默认图按 30MB 总包核算（不构成威胁）。

> **给美术侧的一句话**：§5.5 按 **情形 C** 执行——**默认图只对进首包资产出、且走降规格**（无 alpha 用 JPEG、含 alpha 用低质量 PNG；必要时用自定义构建插件降半分辨率）；**源工程仍留全分辨率无损 PNG**。§5.4 的"有保底"因此成立且不爆包。

### 1.2 纹理压缩格式支持

**官方来源 1**《资源纹理压缩》（`developers.weixin.qq.com/minigame/dev/guide/performance/perf-action-texture-compression`）——各设备平台支持的压缩纹理格式**最大集**：

| --- | --- |
| iOS | ASTC、PVRTC、**ETC1（仅高性能模式）** |

| Windows / Mac | DXT5、DXT3、DXT1、BC4/5/7 |
| 开发者工具 | DXT5、DXT3、DXT1、BC4/5/7 |

> 官方结论原话："通常情况下，移动设备平台推荐使用 **ASTC**。"

**官方来源 2**《游戏资源压缩指南》（`gamemp.weixin.qq.com/doc/overseas-game/guide/grcg.html`）原文要点：

### 1.3 文字缩放 / 无障碍

**官方来源 1**《wx.getSystemInfo》（小游戏 API，`developers.weixin.qq.com/minigame/dev/api/base/system/wx.getSystemInfo.html`）返回字段原文：

> `fontSizeSetting` number — 用户字体大小（单位px）。以微信客户端「我-设置-通用-字体大小」中的设置为准。**[最低版本 1.5.0]**

> 同页首行原文："从基础库 **2.20.1** 开始，本接口停止维护，请使用 `wx.getSystemSetting`、`wx.getAppAuthorizeSetting`、`wx.getDeviceInfo`、`wx.getWindowInfo`、`wx.getAppBaseInfo` 代替。"

**官方来源 2**《小程序适老化设计指南》（`developers.weixin.qq.com/miniprogram/design/elderly.html`）：给出 `fontSizeSetting`（用户字体大小）与 `fontSizeScaleFactor`（字体缩放倍率）的档位规则（iOS 7 档 / Android 8 档），并提供"适老化**自动适配工具**"。**注意：该指南面向「小程序」，不是「小游戏」。**

**逐项判定（对应美术 §9 的可访问性分级）：**

| 能力 | 判定 | 说明 |
| --- | --- | --- |
| **字号跟随系统（平台自动适配）** | ❌ **小游戏不适用** | 小游戏是 **canvas 渲染**，没有小程序的组件体系；官方的"适老化自动适配工具"与组件级无障碍**不覆盖小游戏**。小游戏**只能读取** `fontSizeSetting` 这个值，平台**不会**帮你自动缩放 |
| **读系统字号并手动适配** | ⚠️ **有代价地可行** | 可读 `fontSizeSetting`（基础库 1.5.0+，推荐改用 `wx.getAppBaseInfo`），然后**自己在 canvas 内**按倍率缩放字号 |
| **游戏内文本缩放（×1.15 / ×1.3）** | ✅ **可行** | canvas 内文本完全由游戏自己渲染，缩放是实现层行为，**与平台无关**——反而比依赖平台更可控。可承载 §9 的 Standard 档"文本缩放"承诺 |
| **屏幕阅读器 / ARIA 无障碍** | ❌ **未能从官方文档确认** | 无障碍/ARIA 相关文档均面向小程序基础组件（view/text/button…），小游戏为 canvas，**未能确认存在等价能力** |

**给美术 §9 的直接结论：**

1. **Basic 档**（对比度、不靠颜色、触控区）→ ✅ 可完全达标（与平台无关）。
2. **Standard 档**的"文本缩放 + 减弱动效 + 色盲模式" → 若要落地，**必须全部做在游戏 canvas 内自建**（游戏内设置项），**不要**表述成"跟随微信系统字号"（小游戏无此自动能力）。
3. §9 里"跟随系统字号"的外部事实声明 → 更正为：**平台提供用户字号参数，但不提供自动适配；适配由游戏自建。**

## 2. Cocos Creator 3.8.8 引擎能力（对应美术 §7 的三状态方案）

> 美术侧核心省钱方案：**不出 3 套店铺立绘**，让「未解锁 / 已解锁未开业 / 已开业」（S1/S2/S3 三态）**共用同一张贴图**，差异由 **1 个材质自发光参数 + 1 张叠加层 + 2 个小图标**承担（对齐《美术圣经》§7.6；"已关店" S4 已于 2026-09-14 随关店功能移除，资产口径以 §7.6 为准）。

### 2.1 能否对同一 Sprite 运行时切换材质参数 —— ✅ **可行（且是官方标准用法）**

**官方来源**：Cocos《2D 渲染对象自定义材质》（`docs.cocos.com/creator/3.8/manual/zh/ui-system/components/engine/ui-material.html`）原文要点：

> - 2D 渲染对象的自定义材质是"拓展 2D 渲染对象表现……的最佳实践，可以通过自定义材质实现**溶解、外发光**等渲染效果"。
> - "2D 渲染对象**并不支持多材质，自定义材质的数量最多为一个**。"
> - "请使用 **builtin-sprite** 或 **builtin-spine** 等 2D 专用 Shader 来自定义材质，请勿选择其他 3D 组件使用的 shader。"
> - "如果用户希望修改自定义材质的属性，可通过获取 2D 渲染组件上的 **customMaterial** 来进行操作：
>   `let spriteComp = this.node.getComponent(Sprite); let material = spriteComp.customMaterial; material.setProperty(propName, val)`"

**官方来源（API）**：`MaterialInstance`（`docs.cocos.com/creator/3.8/api/zh/classes/material.materialinstance.html`）提供 `setProperty(name, val)` 等方法，可运行时定制实例。

**判定：✅ 可行。** 走哪条路：

| 路径 | 可行性 | 适用性 |
| --- | --- | --- |
| **自定义 2D Shader（基于 builtin-sprite）+ `customMaterial.setProperty`** | ✅ **推荐** | 一个 uniform 承载自发光强度；状态切换 = 改一个 uniform 值 |
| 顶点色（`v_color`） | ✅ 可行 | 可用于整体明暗，但难以表达"自发光/遮罩"语义，不如 uniform 直观 |
| Shader uniform（同上，本质一致） | ✅ 可行 | 同第一行 |
| **多个 Material 变体**（3 个 Material 资产，同贴图、不同参数） | ✅ 可行 | 也可行；每状态切 `customMaterial` 资产 |

**推荐实现**（供 M04 落地）：

- **一份自定义 2D 材质**（effect 继承 `builtin-sprite`），暴露一个 uniform（如 `u_emissive`）。
- 运行时按状态 `material.setProperty('u_emissive', 0.30 / 1.00)`（**两档**：S1 未开放 = 0.30；S2 待开业 / S3 营业中 = 1.00。对齐《美术圣经》§7.2 / §7.6；原 `0.30 / 0.45 / 1.00` 三档中的中间档仅供 S4「已关店」，随关店移除而收敛）。
- 遮罩/卷帘用**独立子节点 Sprite**（各自 `SpriteFrame` + 透明度），不用材质实现。
- 结果：**同一张贴图、两种自发光档位（S1 暗 / S2·S3 亮），切换瞬间完成、无加载、无闪烁**——完全符合美术 §7.6 的诉求。
- 与美术设想的 `mat_shop_locked/empty/open` 对照：**推荐"一份材质 + 运行时参数"而不是 3 个资产**，因为前者状态切换最轻（只改 GPU uniform），也免维护 3 份资产。若美术坚持 3 个预设资产，也完全可行。（原四态期的 `mat_shop_closed`「已关店」已随 S4 移除，见《美术圣经》§7.5 / §7.6。）

### 2.2 微信小游戏平台上自定义 Shader / 材质有没有限制 —— ✅ **可行（官方未设限），需真机复验**

- Cocos 官方《2D 渲染对象自定义材质》**未标注任何微信小游戏平台的额外限制**。
- Cocos 发布微信小游戏是**官方一等公民路径**（`docs.cocos.com/creator/3.8/manual/zh/editor/publish/publish-wechatgame.html`），effect 随构建产出。
- **首包体积影响**：自定义 effect 是项目内的**小文本资产**，体积可忽略；Cocos 引擎自微信 7.0.7 起作为**插件内置**于微信客户端（第三方资料一致），引擎代码不占主包 4MB。→ **不会因首包体积而不可能使用**。
- 小游戏运行在 **WebGL** 环境（非标准浏览器，无 DOM/BOM），自定义 shader 走 Cocos 的 effect → GLSL 编译流程，属引擎支持路径。
- **判定：✅ 可行，无已知平台阻断。** 备注：**未从官方文档找到"微信小游戏不支持自定义 shader"的任何表述**，也未找到"支持"的逐条明文——属"官方未设限、按引擎通用能力"。因此**必须在真机上复验**（见 §3）。

### 2.3 若不支持或代价过高的降级路径 —— ⚠️ 预烘 PNG 变体（有代价地可行）

**触发条件**（正常不会触发）：真机复验发现自定义材质在小游戏上异常，或团队决定不引入自定义 shader。

**降级方案**：**预烘 PNG 变体**——把"未解锁 / 已解锁未开业 / 已开业"（S1/S2/S3 三态）各出一张**已烘焙好自发光与遮罩**的 PNG，状态切换 = **换 `SpriteFrame`**。

**成本（以美术 §7.6 的三状态 / 5 铺位为口径）：**

| 维度 | 代价 |
| --- | --- |
| **资产数量** | 从"7 张（共用）"上升到"每状态各一套"。可按"自发光差异"归并（S2/S3 同为亮、S1 为暗），实际约 2× 立绘/铺位底图量 |
| **包体积增量** | 约多一套立绘 + 铺位底图 PNG（按美术 §5.5，二层 3 张 ≤70KB、一层 2 张 ≤90KB 量级），估算 **+300～500KB**，可进分包 |
| **状态切换代价** | 换 `SpriteFrame` 是资源引用切换。**若变体已预加载 → 不闪**；**若未预加载 → 首次切换触发异步加载，可能闪烁或卡顿**。因此降级必须**预加载全部状态变体**，代价是**常驻内存升高** |

**判定：降级可行，但明确不如方案 2.1 划算**（资产多、内存高、切换有潜在闪烁）。**首选仍是"一份材质 + 运行时 setProperty"**。
