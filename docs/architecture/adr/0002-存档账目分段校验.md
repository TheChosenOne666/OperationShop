# ADR 0002：存档账目分段校验

- **状态**：**已决议，待实现**（M01 已实现其退化形态；v2 分段形态规划在 M02）
- **日期**：2026-09-14
- **决策范围**：M01 已有基线；M02 落地
- **相关文档**：《玩法与技术方案（草案）》B5.2 存档 schema、B5.3 校验规则调整
- **前置 ADR**：ADR 0004（配置外置与规则指纹）

---

## 背景

M01 的存档被设计成**「可自证」**：`NewService` 加载存档时会用 `validateState` 重新算一遍所有账目，任何对不上的字段都直接拒绝加载，而不是信任文件内容。M01 里每家店只用一个固定单价，所以自证只需要一条恒等式：

```
shops[i].revenue == shops[i].visitors × config.shops[i].coinsPerVisitor
```

进入 v2 后，单客收益不再恒定——**升级**与**所在层满铺加成变化**都会改变单价（草案 A3）。一旦单价在一天里变过，用「累计客流 × 当前单价」去校验历史收益必然对不上：早段的客人是按旧价结算的。

于是必须决定：**存档要不要保留「按单价分段的账目」，还是退化成只校验金币总数？**

---

## 决策

**采用分段强校验（草案方案 A）。** 每家店的累计收益改为按「单价变化点」切分的分段记录：

```
shops[i].segments = [ { unitPrice, visitors, revenue }, ... ]
```

校验时对**每一段**要求 `revenue == visitors × unitPrice`，同时保留金币恒等式（v2 含支出项）：

```
coins == initialCoins + Σ(所有分段 revenue) − spent
```

单价变化只有两个触发点（升级、满铺状态变化），因此每店的分段数有界、总量可控；实现成本只是**每次改价时 append 一条新段**。

**M01 的关系：** M01 已经是这一方案在「单价恒定」下的退化形态——`validateState` 里的 `shop.Revenue != shop.Visitors*price` 等价于「只有一个分段的分段校验」。v2 只是把那个隐式的单段显式化。

### 随附决策：放宽「未开业店铺不得有累计客流」

M01 的校验含一条 `(!shop.Prepared && shop.Visitors != 0)` → 拒绝「未开业店铺有累计客流」。

v2 必须**放宽**为：**「未解锁铺位不得有累计客流与收益」**。

原因：v2 引入**关店**（草案 A2 / 需求 R-03）。关店后 `prepared=false`，但**累计客流与累计收益必须原样保留**（关店不退款、不损失已产生收益）。若沿用「未准备即不得有累计」的旧规则，玩家一关店，存档立刻自证失败、被拒绝加载——这等于「关店即毁档」。因此判定基准必须从**「是否开业」**上移到**「是否已解锁」**：

- 未**解锁**铺位：不得有任何累计客流与收益（空铺不该有账）。
- 已解锁但**关店**：可以有累计客流与收益（这是正常历史）。

---

## 后果（含代价）

**收益：**

- 保留 M01 的「存档自证」基线：一份被手工改过的存档（改金币、改客流、改单价）无法通过校验，会被明确拒绝加载而不是「假装新玩家」。
- 历史账单不可被追溯改写：升级只影响**此后新增**的分段，符合需求 R-07「升级后新产生的收益按新等级计算，历史收益不被追溯改写」。
- 给出逐笔可追溯的账目，M06「店铺详情弹窗」要展示的单店累计数据可以直接从分段汇总。

**代价：**

- 存档结构变复杂：`ShopState` 要从单一 `visitors/revenue` 扩展为 `segments[]`（或在其上保留聚合值），是 schema v1 → v2 的一次不兼容变更。
- 每次改价要多写一条分段，结算热路径上多一个 append 与一次单价比较（可忽略，但需要在 M02 的测试里覆盖「单价变化时账单分段正确」这一边界）。
- 必须显式区分「未解锁 / 已解锁未开业(关店) / 已开业」三态，否则无法正确表达放宽后的校验规则。

---

## 被否决的方案及原因

### 备选：方案 B —— 只校验金币恒等式

不存分段，只保留一条总数校验：

```
coins == initialCoins + Σrevenue − spent
```

**为什么否决：**

1. **放弃自证基线的代价过高。** M01 已把「存档能自证账目」当作设计基线（`validateState` 逐店逐笔重算）。退化成单条恒等式后，只要玩家让「金币总数」与「累计收益」自洽，就能凭空造出客流与收益——**一份被改过的存档无法被发现**，而这正是 M01 明确要防的事（需求文档 4.7：存档损坏/被改不得静默清零，要暴露）。
2. **省下的成本很小。** 分段方案的实现只是「单价变化时 append 一条」，并不需要额外的存储引擎或复杂度；用这条恒等式换来的"省事"与失去的可检测性不成比例。
3. **与好友排行榜（A7）冲突。** 排行榜信任服务端金币，服务端若连自己存档被改都发现不了，排行榜的权威性只是名义上的。

**结论：** 保强校验，采用方案 A。
