# ADR 0001：服务端权威与客户端零计算

- **状态**：已采纳（M01 已实现，后续模块必须沿用）
- **日期**：2026-09-14（回溯记录 M01 已有决策）
- **决策范围**：全部模块（M01 起生效，M02 / M06 / M07 不得回退）
- **相关文档**：《玩法与技术方案》B2 职责红线、B3.6 同步节奏

---

## 背景

《街角百货铺》是微信小游戏，客户端运行在玩家可控的 JS 沙箱里，存档与数值全部可被玩家侧观察甚至篡改。项目的第一版设计红线是「低压力经营、无失败态」，一旦金币/客流可以作弊，好友经营排行榜（A7）立刻失去意义，经济模型（A5）也失去平衡基础。

需要在两条路之间做一次不可逆的架构选择：**数值算在哪一侧**。这个选择会决定接口契约、存档模型、备份迁移方式和整个作弊面。

---

## 决策

**所有游戏数值只在服务端计算；客户端只能提交「意图」，不能提交任何数值或时间。**

具体落地为三条硬契约：

1. **命令体只接受空 JSON 对象 `{}`。** 客户端不得上报金币、时间、客流或任何状态字段。
   `readEmptyCommand` 显式拒绝任何非空 payload，并返回稳定错误码 `INVALID_COMMAND`，错误文案明确写出「不接受客户端金币、时间或客流数据」。
2. **时间推进由服务端时钟驱动。** `NewService` 通过参数注入时钟（生产环境是 `time.Now`），结算以「上次结算时刻 → 当前时刻」的差值为唯一依据；客户端不跑虚拟时间，界面上的数字永远以最近一次服务端响应为准。
3. **服务端返回「本次发生了什么」而不是「现在是什么」。** 结算响应携带 `earnedCoins` / `visitorsUsed` / `changed`，客户端只负责据此播放补间动画，不做任何数值推导。

---

## 后果（含代价）

**收益：**

- 作弊面被压到最小：客户端能伪造的只有「我要开店 / 我要结算」这个意图，伪造不出任何金额。数值、时间、客流、账目全部在服务端闭环。
- 只有一个时间真相源（服务端时钟），没有「客户端虚拟时间与服务端时间对不齐」的二义性。
- 存档是单份服务端权威数据，好友排行榜（A7）可以直接信任金币字段。
- 结算逻辑集中在一处（`Service.accrue`），便于测试与后续扩展（解锁 / 升级等写操作都走同一套原子操作；**关店功能已于 2026-09-14 被用户移除，不再列入**）。

**代价：**

- **客户端必须联网才能推进游戏**。彻底离线时不能兜底产出（这是有意为之：需求文档 R/? 与设计原则 1「不惩罚离线」指的是不扣已有资产，不是离线发钱）。
- **每次到店都要一次服务端往返**。B3.6 因此把轮询节奏定为 5 秒一次，并规定切后台停止、回前台拉快照，将请求量与结算间隔对齐。
- **服务端必须自带防重放/防重复提交**：因此 M01 有了互斥锁串行化、幂等准备、时钟回退拒绝（见 ADR 0002 与《架构现状》并发模型）。
- 接口契约更"窄"：任何新玩法都要先设计服务端命令，客户端不能先跑起来再补服务端。

---

## 被否决的方案及原因

### 备选：客户端计算 + 服务端校验

玩法数值在客户端先算出来（本地累加金币、本地推进时间、本地记录客流），提交结算时把结果上报，服务端做一次校验。

**为什么否决：**

1. **作弊面无法收敛。** 服务端要校验，就必须知道「客户端应该算出多少」，等于要在服务端重复实现一遍同样的计算——那不如直接让服务端算。若校验只是"合理性区间检查"，则玩家只要每次上报考一个略低于上限的值就能稳定刷金，区间校验拦不住。
2. **双份时间模型。** 客户端本地时钟可被玩家任意修改，"离线期间该发多少"要同时维护客户端与服务端两套时间推进逻辑，二者的余量结转、跨业务日切分必须逐位对齐，维护成本极高且极易出现"金币被扣了但界面没变"或"收益被重复计算"（需求文档第七节明确禁止）。
3. **备份与迁移复杂度。** 一旦客户端也持有权威状态，迁移（换设备、清缓存）时必须做客户端状态与服务端状态的合并/仲裁，而 M01 的存档是「损坏就拒绝加载、绝不静默重置」（见 ADR 0004）——两套状态的存在会让"以谁为准"变成持续争论的问题。

**结论：** 校验的成本与重新实现等同，作弊面却不降反升，因此不采用。
