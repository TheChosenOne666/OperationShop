# ADR 0003：客流上限随经营规模动态增长

- **状态**：**已决议，待实现**（M01 为固定值；动态公式规划在 M02）
  - 📝 **2026-09-14 修订（C3-3 / N-2）**：① **冻结时机**由「首次结算」**精确化**为「**首次实际产生客人的结算**」（`openShopCount ≥ 1`），0 店开业时不冻结、不落盘（见「决策」修订注与「后果」）；② **增补**「**未冻结**」状态规格（见「增补（2026-09-14）」一节）。**主决议（客流上限随经营规模动态增长）与「次日生效」结论不变。**
  - 📝 **2026-09-14 修订（N-3）**：「增补（2026-09-14）」§5「校验口径」中，**合法档位集合的等价算术重述下界**由 `baseVisitors` 修正为 `baseVisitors + visitorsPerShop × 1`（`k = 0` 不属于合法档位集合），与集合定义 `{ baseVisitors + visitorsPerShop × k | k ∈ [1,5] }` 对齐。**主决议与其余结论不变。**
- **日期**：2026-09-14
- **决策范围**：M02（数值规则）；影响经济模型与所有解锁/升级决策
- **相关文档**：《玩法与技术方案》A4 客流模型、A5 经济模型

---

## 背景

客流上限决定「一天能结算多少位客人」。它必须选一种增长方式，而这个选择直接决定**开新店是正收益还是负收益**。

M01 的实现里，客流上限是一个固定配置值（`config/development.json` 的 `dailyVisitors = 50`）。如果 v2 沿用固定上限，会出现一个**反向激励**：所有店共享同一批客人，客人按固定顺序轮转，那么开一家**单价低于当前均价**的新店，会把本该落到高价店的客人分走，导致日均收益不升反降。

用固定上限 50、按 A4 的轮转顺序算一遍：

| 已开业店铺 | 轮转单价 | 日均收益（固定 50 客流） | 变化 |
| --- | --- | --- | --- |
| 咖啡 + 花束 | 6, 9 | 375 | — |
| + 衣橱 | 6, 9, 12 | 447 | +72 |
| + 甜屋 | 6, 9, 12, **8** | **435** | **−12（花了 800 金币反而变差）** |
| + 书店 | 6, 9, 12, 8, 10 | 450 | +15 |

关键一行是 **+ 甜屋**：此时在营店铺均价是 **9**（6/9/12 三个价），而甜屋单价 **8** 低于均价，把客人从高价店分流走，日均收益从 **447 掉到 435（净 −12）**。也就是说，玩家**花 800 金币解锁甜屋，结果每天少赚 12 金币**——这是一条明确的反向激励，会直接摧毁「解锁新店 = 变强」的正反馈，也让 800 金币的解锁价失去意义。

---

## 决策

**客流上限随「已开业店铺数量」线性增长，而不是固定值。**

```
每日客流上限 = 基础客流 + 每家已开业店铺 × 单店客流
初版取值：基础 20 + 已开业店铺数 × 15
```

对应档位：

| 已开业店铺 | 客流上限 |
| --- | --- |
| 咖啡 + 花束（2 店） | 50 |
| + 衣橱（3 店） | 65 |
| + 甜屋（4 店） | 80 |
| + 书店（5 店） | 95 |

改成动态增长后，每一家新店都有明确回报：日均收益 375 → 582 → 700 → 855，**每档都是正增量**（+207 / +118 / +155），解锁成本才有意义。

**上限在「当日首次『实际产生客人』的结算」时冻结并写死当日值**（冻结前提 `openShopCount ≥ 1`；草案 B5.2 的 `dailyVisitorCap`）：当天中途开店**不补当日客流**，次日生效。否则「当天中途开店会即时改变当日上限」，与「当日上限不变」的需求（R-05）冲突。

> **修订（2026-09-14，C3-3）：锁定时刻由「首次结算」精确化为「首次产生客人的结算」。**
>
> 原文为「**上限在每天业务日第一次结算时确定并写死当日值**」——**该口径已被推翻**。原因：客户端进入主界面后**每 5 秒轮询一次结算**，会**先于玩家开店**触发当日首次结算；若按「首次结算即冻结」，新账号开局 `openShopCount = 0`，上限会被冻成 `baseVisitors = 20`，与「开局 2 店全开 = 50」（GDD §3.6）自相矛盾，玩家**永远看不到正确的 HUD 分母**。因此冻结必须等到**真的有人开店、且真的开始接待客人**。
>
> **本次修正的性质（显式声明）**：仅把「锁定时刻」从「首次结算」**精确化**到「**首次产生客人的结算**」，**不改变**本 ADR 的冻结语义——**一旦有店开业、且开始接待客人，当日上限即锁定，中途再开店仍次日生效**；也**不改变**「次日生效」的结论。**0 店开业时上限不冻结、不落盘**（「未冻结」状态规格见下方「增补（2026-09-14）」一节）。

> **与 M01 的关系：** M01 的 `dailyVisitors = 50` 恰好等于公式在「2 店」时的取值（20 + 2×15 = 50），因此 M01 与 v2 在**开局档位上是数值一致的**；差别只在于 3/4/5 店时 M01 会停在 50，而 v2 会继续增长。M02 要把 `dailyVisitors` 从固定标量改成「基础 + 单店」两个参数。

## 增补（2026-09-14）：客流上限「未冻结」状态规格（N-2）

**背景**：本 ADR 原文只定义了「**冻结后**当日上限不变」，**完全未覆盖「首次产生客人之前」的状态**——即 `dailyVisitorCap` 尚无值时的表示。该缺口（编号 **N-2**）由 M02 验收口径评审（`docs/M02-验收口径评审.md` §6.3）提出，现补齐。以下五项规格与 GDD《系统-经营与成长》**§5.7** 完全一致。

### 1. 表示方式（存档字段）

| 字段 | 类型 | 含义 |
| --- | --- | --- |
| `capFrozen` | bool | 当日客流上限是否已冻结。**唯一判据**。初值 `false` |
| `dailyVisitorCap` | int | **仅当 `capFrozen == true` 时有效**；`capFrozen == false` 时**无定义、被所有读取方忽略** |

- **不采用 `0` 作哨兵**：`0` 是合法整数域成员，用它表示「未冻结」会与「上限为 `0`」混淆；且未来若 `baseVisitors` 调整为 `0` 会直接撞车。判据**只能是 `capFrozen`**，**不得**用 `dailyVisitorCap` 的取值反推冻结状态。
- **为什么用显式 bool，而非 nullable（`*int` / JSON `null`）作存档表示**：① 存档是 Go 结构体，`bool` 无 nil 判空分支，零歧义、零 panic 面；② JSON 里 `null` 与「字段缺失」客户端难以区分；③ 与「状态用显式标志位表达，而非魔法值」的既有风格一致。

### 2. 字段归属（存档，非 config）

- `capFrozen` 与 `dailyVisitorCap` 均为**存档（运行时状态）字段**，**不是 config**——**不写进规则配置**，否则会被 **ADR 0004** 的配置指纹逻辑误判为规则变更（进而错误地拒绝全部既有存档）。

### 3. 落盘与原子性

- 存档**同时持久化** `capFrozen` 与 `dailyVisitorCap` 两个字段。
- `capFrozen == true`：`dailyVisitorCap` 落盘为冻结值 `baseVisitors + visitorsPerShop × openShopCount`（`openShopCount` = **冻结瞬间**的已开业店铺数）。
- `capFrozen == false`：`dailyVisitorCap` 落盘值**规范化为 `0`**（纯占位），且被**所有读取方忽略**。
- **写入时机**：当日**首次实际产生客人的结算**时，**在同一笔「先落盘再发布」事务内**原子地置 `capFrozen = true` 且写入 `dailyVisitorCap`——避免「冻结了但没落盘」或「落盘了但没冻结」的中间态。
- **0 店开业的结算**：`changed = false`，**不写** `capFrozen`、**不写** `dailyVisitorCap`（保持 `false` / `0`）。
- **跨业务日**（`Asia/Shanghai` 0 点）：`capFrozen` 重置为 `false`、`dailyVisitorCap` 重置为 `0`（回到「未冻结」）。

### 4. 接口暴露

- 快照与结算返回体**同时暴露** `capFrozen`（bool）与 `dailyVisitorCap`（int \| null）：
  - `capFrozen == false` ⇒ `dailyVisitorCap` 返回 **`null`**（API 层把存档占位 `0` 转成 `null`，客户端**永远看不到 `0`**）。
  - `capFrozen == true` ⇒ `dailyVisitorCap` 返回整数冻结值。
  - **服务端保证不变量**：`dailyVisitorCap == null ⟺ capFrozen == false`（二者不可能漂移）。
- **HUD 显示规则**（客户端）：**未冻结**时客流区显示占位 **`— / —`**（或「今日客流：待开始」），**不显示分母**，**禁止**显示 `已到店 / 0` 或 `已到店 / 20`；**已冻结**时显示 `visitorsServed / dailyVisitorCap`。客户端**必须以 `capFrozen` 为闸**：为 `false` 时不渲染分母、不自行填充任何默认上限。

### 5. 校验口径

| `capFrozen` | `dailyVisitorCap` 必须满足 | 说明 |
| --- | --- | --- |
| `false` | **`== 0`** | 未冻结 ⇒ 占位值必须为 `0`；非 `0` 视为存档损坏 |
| `true` | 落在**合法档位集合** `{ baseVisitors + visitorsPerShop × k \| k ∈ [1,5] }` | 等价算术重述：`baseVisitors + visitorsPerShop × 1 ≤ dailyVisitorCap ≤ baseVisitors + visitorsPerShop × 5`，且 `(dailyVisitorCap − baseVisitors) mod visitorsPerShop == 0` |

- ⚠️ **下界是 `base + per × 1` 而非 `base`**：`k = 0`（即 `dailyVisitorCap == baseVisitors`）**不属于**合法档位集合——冻结前提为 `openShopCount ≥ 1`，故 `k ≥ 1`。若写成 `base ≤ v` 会错误地放行 `v == baseVisitors`。

- **为什么用「合法档位集合」而非「按当前 `openShopCount` 重算」**：当日中途开店**次日生效**，冻结后 `openShopCount` 仍可继续增长，但**当日上限不变**，因此**无法**从存档的当前状态反推冻结瞬间的 `k`。可判定的最强不变量就是「值必属合法档位集合」（`k` 恰为冻结瞬间的开业数，取 1–5 的整数）。
- **派生不变量**：与冻结前提 `openShopCount ≥ 1` 联立 ⇒ **`capFrozen == true` 的存档必然至少有一家店处于「营业中」**（关店已移除，开业只增不减，故该不变量稳定成立）。

## 后果（含代价）

**收益：**

- 消除反向激励：「解锁新店」在任何档位都是正收益，消费出口（A5）成立。
- 与满铺加成（A3）配合，形成「先凑满一层、再解锁下一层」的真实取舍。

**代价：**

- 客流上限从「一个常量」变成「一个依赖当日已开业店铺数的派生量」，服务端与客户端都要按同一公式显示分母（HUD 的「已到店/上限」，需求 R-09）。一旦两侧公式不一致，会出现分母对不上。
- 上限必须在**当日首次「实际产生客人」的结算时**（前提 `openShopCount ≥ 1`）**冻结**并落盘（`dailyVisitorCap`），否则当天开店会回溯性地改变当日上限；**0 店开业时不冻结、不落盘**。这给存档增加了一个必须校验的字段（草案 B5.3：上限要「与存档中的 `dailyVisitorCap` 一致，且不超过理论上限」）。
  > **修订（2026-09-14，C3-3）**：原文为「上限必须在**业务日切分时**冻结并落盘」。与上方「决策」同源修正——冻结发生在**首次实际产生客人的结算**（`openShopCount ≥ 1`），而非「业务日切分」或「首次结算」；冻结语义与「次日生效」结论不变。
- 数值需要实机手感确认：基础值 20 与单店值 15 都是开发期初版，属于 M09 前需复核项。

## 被否决的方案及原因

### 备选一：固定客流上限（M01 现状延续）

按上表，固定 50 会让「解锁甜屋」造成 −12 金币/天的净损失。放弃。

### 备选二：客流上限固定，但让新店「不参与分流」（专客专店）

给新店配独立客流，不与他人共享。**否决原因**：这等于每店一套独立结算，客人不再是「商场的客人」而是「店铺的客人」，破坏 A1 的核心循环（客人按固定顺序轮转走遍已开业店铺），也让满铺加成、跨店取舍全部失去意义。

### 备选三：用百分比形式的加成去抵消（例如给低价店补偿）

用复杂的单店权重或补偿系数去平衡。**否决原因**：草案 A3 已明确为「固定 +1 而非百分比」，理由是百分比会产生小数与取整误差、玩家看不懂、服务端难校验。用权重补偿属于同类问题，会重新把数值变成一团难以自证的浮点。

**结论：** 采用「基础 + 单店 × 15」的线性增长，直观、整数、可自证。
