# ADR 0004：数值与规则全部外置到配置

- **状态**：已采纳（M01 已实现，含「配置变更即拒绝旧存档」）
- **日期**：2026-09-14（回溯记录 M01 已有决策）
- **决策范围**：全部模块
- **相关文档**：《玩法与技术方案》B5.1 规则配置、B5.4 版本兼容、B6 存档与容错

---

## 背景

「数值全部是开发期初版，要反复调」（需求文档待确认项 4、A5）。如果数值写死在代码里，每调一次都要改代码、重跑测试、重新构建。项目还有一条更隐蔽的风险：**存档是服务端权威且可自证的**（ADR 0002），数值一旦改变，旧存档里按旧规则记的账目就不成立了——如果处理不当，玩家会看到金币、客流与规则对不上的状态。

因此要做两个绑定的决定：**(1) 数值从代码里拿出来；(2) 规则变化时旧的、规则不匹配的存档怎么处理。**

---

## 决策

### 决策一：所有数值与规则外置到配置文件

规则版本、初始金币、日客流、结算间隔、业务时区、五店收益表全部在 `config/development.json`，由 `LoadConfig` 读入并通过 `Config.Validate` 强校验。**代码里不出现任何游戏数值常量。**

- 配置读取是**严格 JSON**：`decodeJSON` 用 `DisallowUnknownFields` 拒绝未知字段，并要求「恰好一个 JSON 值」（拒绝多值、尾随 garbage、顶层数组、`null` 等）。配置里写错字段名会**启动即失败**，而不是静默取默认值。
- `Config.Validate` 拒绝越界值（金币、客流、间隔、时区、店铺位置/数量/单价），要求业务时区必须是 `Asia/Shanghai`，且恰好是两层五店、位置与 ID 一一对应。

### 决策二：配置一变，旧存档被拒绝加载（而不是被重置）

服务端用**规则指纹 `RulesFingerprint`** 把存档与「生成它时的规则」绑定：

- 指纹 = 对**整个 `Config` 做 JSON 序列化后取 SHA-256**（`fingerprint`）。
- 存档里存下生成时的指纹；每次加载都重算当前配置的指纹并与存档比对。
- **任何不一致 → 拒绝加载**，报错「schema or rules changed; use a separate development save」，且**绝不用默认状态覆盖原存档**。

这是一条看似激进的行为，但它是有意的：**规则变了，旧存档的账目就不成立，静默重置比报错更危险。**

- 静默重置 = 玩家数据在无感知的情况下被清空。用户以为"数据还在"，实际已被清；这违反需求文档 4.7「不得静默清零，必须明确暴露」。
- 报错 = 明确告诉操作者"规则变过了，请换一份存档"。开发期没有真实用户，正确动作是**删掉旧存档重建**；上线后这个行为会与「账号级迁移策略」一起重新设计（列入 M07/M09）。

## 后果（含代价）

**收益：**

- 调数值只改 JSON、不改 Go 代码，也不改测试逻辑（`internal/game` 的测试从 `config/development.json` 读取，天然跟随）。
- 严格 JSON + `Validate` 让「配置写错」在**启动时**就暴露，而不是运行时产生诡异数值。
- 指纹机制让「规则/存档不匹配」在**加载时**就被拦下，不可能出现"按新规则解释旧账"的错账。

**代价（这条决策的代价必须写清楚）：**

- **指纹覆盖整个 `Config`，包括与数值无关的字段。** `Shops[].Name`（店名）和 `Shops` 的**顺序**都参与指纹——改一个店名、或把配置里的店铺顺序换一下，也会让旧存档失效。这是刻意的保守选择（宁可多拒，不可错算），但代价是：**任何配置改动都要删档重建**。测试 `TestChangedRulesDoNotReuseSave` 专门锁定了这一点（规则版本、初始金币、日客流、结算间隔、收益、店名、顺序，任一改动都拒绝旧存档）。
- **没有迁移工具。** M01 明确接受「开发期直接删档」这一成本（草案 B5.4）；一旦上线有真实用户，这个决策必须被 M07 的账号级迁移方案取代，否则等于"每次调数值，所有玩家清档"。
- 指纹算法与 `Config` 的 JSON 形态（字段名、字段顺序、切片顺序）**强耦合**：给 `Config` 增删字段会天然改变指纹（预期），但若在实现中把 `Config` 换成非 JSON 可序列化的结构，`fingerprint` 会静默失真——`fingerprint` 的实现里已注明「Config 只含 JSON 可序列化的标量与切片」这条前置假设。

## 被否决的方案及原因

### 备选一：数值写死在代码里（常量 / 直接内联）

调数值要改代码、重跑测试、重新构建。与「数值是开发期初版、要反复调」直接冲突（规划原则 4：数值不写进代码）。否决。

### 备选二：写迁移工具 / 版本兼容层（旧存档升到新规则）

**为什么当前否决：** 草案 B5.4 明确「上线前没有真实用户，开发期直接删除旧存档文件即可，不需要写迁移工具」。写一套"把 v1 存档换算成 v2"的迁移逻辑，在**规则每一次都可能变**的开发期是纯粹的成本，且迁移本身容易引入错账。此方案**不是永久否决**——上线后（M07 账号上云）会重新评估。

### 备选三：规则不匹配时静默重置为默认状态

**为什么否决：** 这正是需求文档 4.7 明令禁止的「假装新玩家」。静默丢数据的后果比拒绝启动严重得多。否决。
