## 一、模块范围

M02 在 M01 的服务端权威闭环上**只做扩展**，不改变架构与信任边界。

包含：

- 规则配置 v1 → **v2**：`dailyVisitors` 标量 → `baseVisitors + visitorsPerShop`；`shops[].coinsPerVisitor` 标量 → `shops[].levelCoinsPerVisitor`（5 元等级单价表）；新增 `slots[]`（铺位解锁顺序与价格）、`fullFloorBonus`、`upgradeCosts`；`shops` 数组顺序改为**一层临街优先**。
- 存档 schema v1 → **v2**：新增 `spent`、`capFrozen`、`dailyVisitorCap`、`unlockedSlots[]`、`shops[].level`、`shops[].segments[]`。
- 新增两条命令：解锁铺位、升级店铺。
- 客流上限从「固定 50」改为「随经营规模增长」，并把「未冻结」做成显式二态。
- 账单分段（ADR 0002）：每次单价变化 append 一段，逐段 `revenue == visitors × unitPrice` 自证。
- 校验规则调整：金币下界放宽为 `coins >= 0`，金币恒等式加 `− spent`。

不包含（留给后续模块）：客户端与登录、好友/排行/互访/广告、布局调整与装修、多账号与云端存储、手动关店（第一版不做）。

## 二、运行方式

与 M01 完全一致（环境变量、启动命令、仅本机限制均未变），只把配置与存档换成 v2 形态。开发期存档 schema 变更会让旧存档被拒绝加载，**直接删除开发存档文件即可**，不需要迁移工具。

除健康检查外，所有接口都需要 `Authorization: Bearer <MALL_DEV_TOKEN>`；带 `Origin` 头时必须命中白名单；命令接口只接受空 JSON 对象 `{}`。

| 方法 | 路径 | 入参 | 出参 | 相对 M01 |
| --- | --- | --- | --- | --- |
| GET | `/healthz` | 无（免令牌） | `{status, mode, wechatLogin}` | 不变 |
| GET | `/api/v1/config` | 无 | 规则配置（v2 全量） | 结构变化 |
| GET | `/api/v1/mall` | 无 | 客户端快照 `MallView`，不结算、不刷新日期 | 结构变化 |
| POST | `/api/v1/shops/{id}/prepare` | `{}` | 一次原子操作结果 | 不变（新增 `SLOT_LOCKED` 拒绝） |
| POST | `/api/v1/shops/{id}/upgrade` | `{}` | 一次原子操作结果 | **新增** |
| POST | `/api/v1/slots/{slotId}/unlock` | `{}` | 一次原子操作结果 | **新增** |
| POST | `/api/v1/mall/settle` | `{}` | 一次原子操作结果 | 不变 |

**两套 ID 不得混用**（GDD §3.2）：解锁接口入参是 **slotId**（`f2-s1`），开店/升级接口入参是 **shopId**（`clothing`）。把 slotId 传给升级接口、或把 shopId 传给解锁接口，都会返回 404 `SHOP_NOT_FOUND`，且零副作用。

### 3.1 命令返回体（`prepare` / `upgrade` / `unlock` / `settle` 共用）

```json
{
  "state": { "...MallView..." },
  "earnedCoins": 6,
  "visitorsUsed": 1,
  "changed": true
}
```

`changed=false` 表示本次请求没有产生任何状态变化，且**不写存档**（例如重复开店、重复解锁、同一时刻重复结算、客流已耗尽）。

未冻结时的同一字段（`capFrozen == false`）：

```json

```

契约保证：`dailyVisitorCap == null` **⟺** `capFrozen == false`（GDD §5.7）。客户端据此显示 `— / —` 且不显示分母，**不得用 `0` 作哨兵**。

`nextSlotId` / `nextUnlockCost` 在全部铺位解锁后为 `null`；`shops[].upgradeCost` 在满级时为 `null`。

`shops[].segments` **不下发给客户端**（账单明细只留在存档里用于自证）；`nextShopIndex` 同样只在存档中。

### 3.3 错误响应

```json
{ "error": { "code": "INSUFFICIENT_COINS", "message": "金币不足" } }
```

| HTTP | code | 触发条件 |
| --- | --- | --- |
| 400 | `INVALID_COMMAND` | 请求体不是空 JSON 对象（客户端塞入金币/时间/客流等） |
| 401 | `UNAUTHORIZED` | 缺少或错误的 Bearer 令牌 |
| 403 | `LOCAL_ONLY` | 主机头或来源地址不是本机回环地址 |
| 403 | `ORIGIN_DENIED` | 浏览器来源不在白名单内 |
| 404 | `SHOP_NOT_FOUND` | 店铺 ID 未知；**铺位 ID 未知也复用此码**（见第七节 §7.1） |
| 409 | `SLOT_LOCKED` | 目标铺位尚未解锁（对未解锁铺位开店，或升级未解锁铺位的店铺） |
| 409 | `SLOT_ORDER` | 试图跳过顺序解锁二层铺位 |
| 409 | `SHOP_NOT_OPEN` | 对「待开业」店铺升级 |
| 409 | `MAX_LEVEL` | 已满级仍请求升级 |
| 409 | `INSUFFICIENT_COINS` | 金币不足（解锁或升级） |
| 409 | `CLOCK_BACKWARDS` | 服务器时钟回退，暂不结算 |
| 409 | `NUMERIC_LIMIT` | 存档触及安全整数上限，拒绝写入部分结果 |
| 413 | `BODY_TOO_LARGE` | 请求体超过 1 KiB |
| 415 | `JSON_REQUIRED` | 请求类型不是 `application/json` |
| 500 | `SAVE_FAILED` | 存档写入失败，本次操作整体回滚 |

所有被拒绝的命令都保证**零变化、不写存档**。

## 五、存档 schema v2

```json
{
  "schemaVersion": 2,
  "rulesFingerprint": "6e297a...854c",
  "revision": 6,
  "coins": 386,
  "spent": 900,
  "businessDay": "2026-09-15",
  "capFrozen": true,
  "dailyVisitorCap": 50,
  "visitorsRemaining": 49,
  "lastAccrualAt": "2026-09-14T16:29:08.5477507Z",
  "lastObservedAt": "2026-09-14T16:29:10.0849536Z",
  "nextShopIndex": 1,
  "unlockedSlots": ["f1-s1", "f1-s2", "f2-s1"],
  "shops": [
    { "id": "coffee", "prepared": true, "level": 1, "visitors": 1, "revenue": 6,
      "segments": [{ "unitPrice": 6, "visitors": 1, "revenue": 6 }] },
    { "id": "clothing", "prepared": true, "level": 2, "visitors": 0, "revenue": 0,
      "segments": [{ "unitPrice": 12, "visitors": 0, "revenue": 0 },
                   { "unitPrice": 14, "visitors": 0, "revenue": 0 }] }
  ]
}
```

- `capFrozen` 是**唯一判据**；`capFrozen == false` 时 `dailyVisitorCap` 落盘占位 `0`，读取方一律忽略该值。
- `unlockedSlots` 始终按 `unlockOrder` 升序、同序按 config 数组顺序**规范化写入**；加载时按**集合语义**校验，非规范顺序本身不是损坏，加载后会被规范化为规范顺序（不重写文件）。
- `shops[].segments` 每店段数上界 **≤ 6**（1 初始 / 开店建首段 + 4 升级 + 1 满铺）；未开业的店铺 `segments` 为 `null`。

### 5.1 存档校验（GDD §5.5）

| 规则 | v2 |
| --- | --- |
| schema / 规则指纹 | `schemaVersion == 2` 且指纹与当前 config 一致，否则拒绝加载并保留原文件 |
| 金币恒等式 | `coins == initialCoins + Σrevenue − spent` |
| 金币下界 | **`coins >= 0`**（M01 的 `coins >= initialCoins` 已放宽，否则玩家一消费即毁档） |
| 逐段账目 | `revenue == visitors × unitPrice`（含空段 `0 == 0 × unitPrice`） |
| 店铺聚合 | `visitors == Σsegments[].visitors`、`revenue == Σsegments[].revenue` |
| 开业与分段一致 | `prepared == (len(segments) > 0)` |
| 未解锁铺位 | 不得已开业、不得有累计客流或收益 |
| `unlockedSlots` | 未知 / 重复 / 数量越界（< 开局铺位数 或 > 铺位总数）/ 缺开局铺位 / 跳序 ⇒ 存档损坏、拒绝加载 |
| 客流上限二态 | 未冻结 ⇒ `dailyVisitorCap == 0 && visitorsRemaining == 0`；已冻结 ⇒ `dailyVisitorCap` 落档位集合 `{base + per × k \| k ∈ [1,5]}`、`visitorsRemaining ∈ [0, cap]`、且至少一家开业 |

## 六、实现要点

### 6.1 `prepare` 的硬顺序（不可调换）

① 置该店 `prepared = true` → ② 重算该层满铺状态 → ③ 为该店建立 / append 分段（`unitPrice` 取**重算满铺之后**的值）。

由此，**触发满铺的新开业店只产生一条 bonus 价段**，不会出现 spurious 的 pre-bonus 空段；同层其他已开业店各 append 一条新段。

### 6.2 账单分段的三个触发点（ADR 0002 / GDD §4.3）

| 触发点 | 行为 |
| --- | --- |
| 开店 `prepare` | 建立**首个**分段 |
| 升级 `upgrade` | 该店 append 一条新价段（历史段原样保留） |
| 满铺状态变化 | 该层**所有**店 append 一条新价段（满铺不可逆，整局至多一次） |

分段只在「空段或末段价与当前单价不同」时 append，避免重复价段刷爆段数。

### 6.3 客流上限的三态迁移

| 状态 | 进入条件 | 落盘 |
| --- | --- | --- |
| 未冻结 | 新建存档、跨业务日重置 | `capFrozen=false`、`dailyVisitorCap=0` |
| 冻结 | **当日首次实际产生客人的结算**（`openShopCount ≥ 1` 且本段确实产出客人） | `capFrozen=true`、`dailyVisitorCap = base + per × openShopCount` |
| 保持 | 当日中途开店 / 解锁 / 升级 | 当日上限不变，次日生效 |

0 店开业时既不冻结也不落盘；跨业务日（`Asia/Shanghai` 0 点）重置为未冻结。

### 6.4 并发与原子性

解锁、升级、开店、结算**共用同一把 `Service.mu`**，并沿用「先落盘再发布、失败整体回滚」：`store.Save` 失败时返回 `SAVE_FAILED`，内存状态与存档都不推进。

### 6.5 配置指纹（ADR 0004）

`fingerprint(Config)` = `json.Marshal(整个 Config)` → SHA-256 → hex。`capFrozen` / `dailyVisitorCap` / `unlockedSlots` / `level` / `spent` / `segments` 是**存档字段、不是 config**，因此不会污染指纹。规则一改，指纹即变，旧存档被拒绝加载并保留原文件。

### 7.5 独立复核后的回修（2026-09-18，SC-M02-QA-004）

复核在 §8.3 记了两项 P1，用户裁定「改实现」与「本轮一并修」，落在此节。规格文本未改动——实现向 GDD 对齐。

**`P1-A` 空闲结算必须 `changed=false` 且不落盘**（GDD §5.7.2）

改前三处（GDD、本文 §7.2 #5、`service_test.go` 注释）都写着「不落盘」，行为却每次轮询都写盘、都递增 `revision`。修在 `internal/game/service.go`：

| 位置 | 改动 | 理由 |
| --- | --- | --- |
| `accrue` 空转分支 | 零开业 / 客流已耗尽时**不再**把 `LastAccrualAt` 推到 `now` | 空闲轮询必须是真正的无操作，否则「有变化」的判定被一个纯游标移动污染 |
| `Prepare` 提交闭包 | 当该店是**当日第一家**开业时，把 `LastAccrualAt` 锚到准备时刻 | 上一行的对偶：原来靠空转轮询随手维持的锚点，改由真正需要它的那笔提交负责写入。后续店铺不锚，保留 `accrue` 已算出的不足一间隔残余，行为不变 |
| `mutate` | 用 `sameCommittedState`（忽略 `lastObservedAt` 的深比较）取代「`now` 与 `LastObservedAt` 完全相等才跳过」 | 无实质变化 ⇒ 不 `Revision++`、不 `Save`、`changed=false` |
| 命令闭包签名 | `func(*State) error` → `func(*State, time.Time) error` | 提交闭包需要结算时刻来锚游标 |

**语义澄清（影响 M04/M05 客户端）**：`Result.changed` 现在严格等于「服务端是否发布了新状态」；快照与响应里的 `lastObservedAt` 语义是**最后一次发布状态的时刻**，不再是**最后一次被轮询的时刻**——空闲期该字段保持不变属预期。`clockBackwards` 守卫仍成立：`validateState` 保证 `LastAccrualAt ≤ LastObservedAt`，两者在空转时一同冻结，故 `now` 一旦回退到已发布锚点之前即被拦下。

**`P1-B` 铺位位置唯一性**（`internal/game/config.go`）

`validateSlots` 增加「两个 `slots[]` 不得共用同一 `(floor, position)`」。未再加「每个店铺必须被铺位覆盖」：在既有的 `len(Shops)==5`、`len(Slots)==5`、店铺位置互异、每铺位必须指向已有店铺位置这几条约束下，覆盖关系可证为该规则的推论，加上即死代码。**改前**：`f2-s3` 与 `f2-s2` 同位置同 `shopId` 的配置能通过 `Validate()`，未覆盖到的店铺在 `buildLayout` 里经 `slotIndex[""]` 静默取到 `Slots[0]`，其解锁门禁与满铺判定读到错误铺位且零报错。

**测试**：4 处被固化成 `changed=true` 的空闲结算断言改回 `false` 并补「游标不推进 / 修订号不变 / 落盘次数不变」；新增 `game.TestSettleDoesNotCommitWithoutChange`（零开业 / 间隔未满 / 耗尽后三种空转 + 跨业务日仍须提交）与 `config` 用例「两铺位同位置且店铺一致」；`api.TestErrorMapping/时钟回退` 改用必定提交的请求推进锚点。

**复验**：用发现缺陷的同一批探针重跑——`P-A` 三次空 settle `revision` 恒为 1、落盘恒为 1 次；`P-B` 同理；`P-F` 现在被 `Validate()` 拒绝；`P-D`（分段上界与 bonus 段）逐字节无回归。端到端重跑 11 条全部维持通过。质量门 `gofmt` / `go vet` / `go test -race` 全绿，覆盖率 `internal/game` 97.3%、`internal/api` 99.1%。
