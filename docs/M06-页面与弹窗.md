## 1. 这一模块解决什么

| 痛点 | 现状证据 | 后果 |
| --- | --- | --- |
| 玩家看不到「这家店赚了多少」 | 主界面只有全局金币与客流两个数（`MallScene.renderHud`），逐店 `visitors`/`revenue` 服务端已返回但界面从不显示 | 单店好坏无法判断，「解锁还是升级」这个核心取舍（R-07/附录 B-2）变成盲选 |
| 两笔最大额不可逆支出没有确认环节 | 解锁 600/800/1200、升级 700～若干，客户端目前点铺位直接发命令（`MallScene.onSlotTouched` 只处理开店） | 误触即扣钱且不可撤销；R-02 要求的「金币不足时给出原因」至今没有任何落点 |
| 开店入口是临时位置 | M05 的「点待开业铺位即开店」是**已裁定的规格偏离**（§八 记录 ①），正式入口是经营页的金色「开业」按钮 | 经营页缺席一天，这条偏离就一天不结案 |
| 飘字金额的口径雷区会常驻 | M05 用「单价取上一份快照」绕过（`docs/M05-经营闭环.md` §14 的 P1-A 修复），但 `unitPrice` 的用途边界仍未定（§八-17-B） | 详情弹窗一显示这个字段，瞬时偏差就变成玩家随时可看到的**常驻错误** |

## 2. 使用场景（玩家路径）

1. **看经营**：主界面 → 底部「经营」→ 今日客流 / 今日收益 / 满铺加成三格概览 → 五家店铺按客流到店顺序排列 → 找「待开业」的那行点「开业」。
2. **升级**：经营页点一家营业中的店 → 详情弹窗看等级、单客收益构成、累计客流、累计收益 → 点「升级到 Lv(n+1)」→ 升级确认弹窗看单价对比 + 花费/现有/余额 + 「不追溯历史」说明 → 确认升级或再想想。
3. **扩铺**：主界面或经营页 → 底部「布局」→ 两层铺位总览（每格三态之一）+ 每层满铺进度 → 底部主按钮「解锁「X」铺位 N 金币」→ 解锁确认弹窗看前后对照 + 三行金币账 + 解锁后会怎样 → 确认解锁或再想想。
4. **出问题时**：任何界面请求失败，提示要能看懂，且数字保留最后一次成功值（M05 已定口径，本模块沿用，不得回退）。

## 3. 逐屏需求点

> 设计稿是**唯一权威形状**：尺寸、色值、文案、状态编码全部按稿执行（@750×1334 基准；稿内「设计说明」面板的规格条目算需求的一部分）。

### 3.1 经营页（稿 02）

| 元素 | 需求 | 口径 |
| --- | --- | --- |
| 概览格「今日客流」 | `已到店 / 上限`，未冻结时整格 `— / —` | `visitorsServed` + `dailyVisitorCap`（未冻结为 `null`）；沿用 §7.2 裁定 L |
| 概览格「今日收益」 | `+N` 金币 | 🔴 **D-2**：服务端无当日增量字段；逐店 `revenue` 是**历史累计**（`ShopState` 注释「cumulative」），跨日不清零，不能当今日数用 |
| 概览格「满铺加成」 | 生效层名（如「一层生效」） | 逐层 `已开业数 / 该层铺位数`（§6.1 允许由 `unlockedSlots`+`prepared` 派生） |
| 说明条 | 「按客流到店顺序排列（一层临街优先）」 | 顺序 = 服务端 `shops` 数组顺序，客户端不自己排 |
| 店铺行 ×5 | 店名、等级徽章、缩略店面、单客收益、累计客流·累计收益、右侧状态或操作 | `shops[].name/level/unitPrice/visitors/revenue` |
| 「单客 8 金币 (7+满铺1)」 | 单价**必须写出基础 + 满铺的构成**（稿内明示：不写玩家看不懂数字为什么变） | 🔴 **D-1**：服务端只给合计 `unitPrice`，无拆分 |
| 状态位「营业中」 | 绿色对勾 + 文字；**不给关店按钮**（关店已于 2026-09-14 移出范围） | `prepared == true` |
| 「开业」按钮 | 待开业行显示，点击开店、无二次确认（R-03：不花金币、幂等） | `unlockedSlots` 含该铺且 `prepared == false` |
| 未开放行 | 文案「未开放 · 需先在布局页解锁铺位（800 金币）」/「需先解锁二层 2 号铺位」，缩略图压暗 + 纱罩 + 锁形 | `slots[]`（`floor`/`position`/`shopId`/`unlockCost`）与 `unlockedSlots` |
| 底部 HUD | 与主界面同一套三导航 + 金币 + 客流；当前页导航钮高亮为按下态 | 复用主界面 HUD 契约 |

### 3.2 布局页（稿 01）

| 元素 | 需求 | 口径 |
| --- | --- | --- |
| 楼层分组标题 | 「二层 · 楼面」「一层 · 临街」+ 右侧 `n / m 已开放` | `slots[]` 的 `floor`/`position` + `unlockedSlots` |
| 铺位卡 | 店名 + 三态之一：`营业中 · 单客 N 金币` / `待开业` / `未开放 · N 金币`；未开放要纱罩 + 锁角标 + 压暗 | `shops[]` + `unlockedSlots` + `slots[].unlockCost`；**三态编码须转灰度仍可分**（稿内硬要求：靠锁 vs 加号、暗 vs 亮、文字三通道，不靠颜色） |
| 满铺加成卡 | 逐层两行：已生效（实心点 + 「该层单客收益 +1（已生效）」）/ 未生效（空心点 + 「再开放 K 个铺位即可获得 +1」） | 计数派生 + `config.fullFloorBonus` 的**显示值**（不得在客户端写 `+1` 这个常量） |
| 主按钮 | 「解锁「甜屋」铺位 800 金币」，可解锁态带金色呼吸光晕 + 加号角标 | `nextSlotId` + `nextUnlockCost` + 该 slot 的 `shopId` 对应店名 |
| 主按钮禁用态 | 金币不足时文字改「再攒 N 金币」（**写出差多少**，不写「金币不足」）+ 锁角标 + 不透明度 78%；**禁止变红**、禁止灰到看不见 | 差额由 `coins` 与 `nextUnlockCost` 得出（见第 4 节 D-4：这条要不要服务端给） |
| 一层铺位卡 | 只显示「营业中 / 待开业」，一层两铺为开局已解锁、无解锁按钮 | `unlockedSlots` 初值 |

### 3.3 店铺详情弹窗（稿 04）

| 元素 | 需求 | 口径 |
| --- | --- | --- |
| 标题行 | 店名 + 等级徽章 + 营业状态 | `shops[].name/level/prepared` |
| 店面示意 | 一张店面图（正式资产未到位时用现成的 `shop_*_open` 占位件） | 复用主界面取图路径 |
| 单客收益 | `8 金币` + 构成条「基础 7 + 满铺 1 = 8」 | 🔴 **D-1** |
| 累计客流 / 累计收益 | `24 位` / `192 金币`，**两行都读服务端原值** | `shops[].visitors` / `shops[].revenue` |
| 升级预告 | 「升到 Lv3 后 单客 9 金币 (+1)」+「升级花费 700 金币」 | 花费 = `upgradeCost`（已有）；升级后单价 🔴 **D-3**（GDD §6.1 那一行写着「该店 `upgradeCost` + 升级后单价」并标 M02 新增，代码里没有） |
| 已满级 | 稿未画（见第 8 节待裁定）；`upgradeCost == null` 即满级，此时不得出现任何「可升级」暗示 | `upgradeCost == null` |
| 金币不足 | 「确认升级」换成禁用态：锁角标 + 文字「再攒 260 金币」+ 不透明度 78%；**点了不发写命令** | `coins` vs `upgradeCost` |
| 关闭 | 点遮罩或右上角关闭钮 = 取消，**不做二次确认**（升级有独立确认弹窗） | 稿内交互说明 |
| 主按钮 | 「升级到 Lv3」→ 打开升级确认弹窗（稿 06），本页不直接提交升级 | — |

### 3.6 跨屏通用要求

- 弹窗一律带遮罩（稿值 `rgba(74,47,30,.58)`）、木面板 + 内嵌奶白内容板（木底压正文对比度不足）、关闭钮直径 64 压在面板右上角外沿。
- 正文落奶白板、按钮高 ≥88 触控区、字号按稿（标题 34 / 正文 25–26 / 辅助 21）。
- 三导航（经营 / 布局 / 好友）在任何一页都在：**好友页属 M08，本模块只保留入口与「未开放」占位，不得做假榜单**。
- 顶部 48px 避让区不放任何信息；HUD 160px + 其上方 53px 禁放区。

## 5. 验收标准

> 对应 `production/开发规划文档.md` §三 M06 那句「逐屏与设计图核对字段、文案、布局、按钮状态；金币不足、已满级等异常态有明确提示且不出错」的具体化。**下面每条都要有可取证的实际读数**，不接受"应该没问题"。

1. **逐屏对稿**：五屏（经营页、布局页、店铺详情、解锁确认、升级确认）各自的字段、文案、布局尺寸（@750 基准）与设计稿一致；三态编码**转灰度后仍可分辨**（形状 + 文字 + 明度三通道齐）。
2. **零本地规则常量**：界面显示的每个数字都能指到最近一次服务端响应的某个字段；客户端代码里不出现等级单价表、解锁价、升级价、满铺值中的任何一个（ADR 0001 / ADR 0004 / `ApiTypes.ts` 的「只读不推」）。
3. **累计口径**：详情弹窗的「累计客流 / 累计收益」逐字等于服务端 `shops[].visitors` / `shops[].revenue`；**不得**用「累计客流 × 单价」现算（单价会变，分段的存在理由就是这笔账不能现推）。
4. **显示金额与入账一致**（§八-17-C 要求补进 M06 的那条）：飘字与详情/升级弹窗上出现的「单客收益」，与该轮服务端实际入账额（`earnedCoins` ÷ `visitorsUsed` 的口径核对）在同一次取证里对得上；不一致就判不通过。
5. **金币不足**：解锁与升级两条路径都给「差多少」的明确文案（不是「金币不足」四个字），且**不发写命令**；按钮保持三重编码的禁用态，不变红。
6. **已满级**：`upgradeCost == null` 时界面不出现任何"可升级"暗示，等级与文案有明确交代（具体形态见第 8 节，需先裁定）。
7. **未解锁铺位**：不因 `unitPrice`/`upgradeCost`/`nextUnlockCost` 有值就渲染成可操作（§8-8 那条边界的正面验收）。
8. **失败不出错态数字**：错误码逐个映射为玩家可读提示（`INSUFFICIENT_COINS`/`MAX_LEVEL`/`SLOT_LOCKED`/`SLOT_ORDER`/`SHOP_NOT_OPEN`/`SHOP_NOT_FOUND`），且失败时界面数值保留最后一次成功值，不跳变、不回退（沿用 M05 验收第 3 条）。
9. **页面切换不放大请求量**：切页、开合弹窗都不额外发请求；轮询节拍不变；后台期间请求数为 0（沿用 M05 的实测口径）。
10. **包体数字**：本模块每次构建都要报主包体积，并记录进文档（M04 起的固定要求）。

## 9.2 后端改动（`internal/game`、`internal/api`）

**a. 逐店单价拆分 + 升级后单价（纯派生，不动存档）**

`unitPrice` 现在一函数混算两件事（`service.go:398-404`）。拆成两个具名派生，再让 `ShopView` 各给一份：

| 字段 | 取法 | 不变式 |
| --- | --- | --- |
| `unitPriceBase` | `cfg.Shops[i].LevelCoinsPerVisitor[level-1]` | — |
| `floorBonus` | `floorFull(state, floor)` 为真时取 `cfg.FullFloorBonus`，否则 0 | `unitPriceBase + floorBonus == unitPrice` |
| `nextUnitPrice` | 下一级的 base + **同一个** `floorBonus`；`level == maxLevel` 时为 `null` | 升级不改满铺状态（`floorFull` 只看 `unlocked`+`prepared`，与 level 无关），故加成不变 |

**b. 当日累计收益 `todayEarned`（动存档）**

- `State.TodayEarned int64` + `MallView.TodayEarned int64`。
- 累加点：`accrue` 的逐客人循环里与 `Coins`/`Revenue` 同处（`service.go:529-533`）。不加溢出分支——`TodayEarned ≤ Σ shop.Revenue`，而 `Revenue` 的 `maxSafeInteger` 门禁已在前面。
- 归零点：`accrue` 的业务日翻转分支（`service.go:483-490`），与 `CapFrozen`/`DailyVisitorCap` 一起重置。
- 自证：`validateState` 补一条 `0 <= TodayEarned <= Σ shops[].Revenue`（与既有账目恒等式同族，不是新式防御）。
- 语义写进注释与 GDD 对表：**只含到店收益，不含解锁/升级支出**（那两笔走 `Spent`，稿上的「今日收益」是 `+332` 这种纯进账）。
- ⚠️ **破坏性变更**：`schemaVersion` 2 → 3。不升的话旧档的 `todayEarned` 反序列化为 0，而当天其实已赚过钱——那会让界面上挂一个**看不出来的错数**，比删档更糟。按 `agents.md` 与 `架构现状` §8-6 的既定取舍，开发期删档重建。**这条要单独点头。**

**c. 写命令日志（§7.2 冲突 E 的收口，可选）**

### 10.1 这一轮改掉的三个真问题

1. **切页后不渲染**（最严重）：`render` 只在服务端状态变化时被调，而空闲 settle 是空转、被
   `revision` 守卫整份丢掉 ⇒ 新页面挂着构建时的占位串，且「营业中/开业按钮/锁牌」三个状态节点
   **同时可见并互相盖住点击**——点「开业」实际命中的是锁牌，走成了跳布局页。
   修法：`show()` 里立刻用当前快照渲染一次（`MallPages.show`）。
2. **`Graphics` 被引擎功能裁剪砍掉**：`cc.Graphics` 不在产物导出表里，`addComponent` 抛
   `Error 3804（Type must be non-nil）`，整个页面层建不起来、Mall 场景启动失败。
   修法：`settings/v2/packages/engine.json` 的 `graphics` 开为 `true` 并加进 `includeModules`
   （等价于在「项目设置 → 功能裁剪」里勾选）。⚠️ **这条会动包体**，任务 8 的体积数字必须体现它。
3. **两处对稿偏差（已按稿修正或按实调整，登记在此）**：
   - 布局页加成卡原本按累计间距算到 1052，压进主按钮（1009）底下 ⇒ 层间距改回稿值 9px、
     卡高 150 → 132；页内错误提示位从主按钮上方移到顶栏右侧（顶栏标题宽度相应 400 → 200）。
   - 经营页行内主文案我一开始写成 26px，稿是 22px ⇒ 22px + 文案去掉「铺位」二字，
     否则「未开放 · 需先在布局页解锁铺位（1200 金币）」会压到右侧锁牌上。
     稿上这一行本身有两套措辞，取带价格的那套为准。

### 10.2 取证通道本身的两条事实（影响后续所有模块）

1. **`window.cc` 只在引擎重构建后的产物里可用**：改功能裁剪会触发重构建，之后 `hud` 步骤才读到
   Label。第一次跑（未重构建的产物）报「页面里没有 window.cc」。所以 `AGENTS.md` 里
   「`hud` 是唯一能归因到显示的是哪个数的手段」这句，前提是产物带得出引擎全局。
2. **Chrome 会复用磁盘缓存**，导致「改了没生效」的假阴性（同一份旧 `cc.js`，报错字节偏移都一致）。
   驱动器已加 `Network.setCacheDisabled`。这条不修，之后每次重建后的取证都可能是读旧产物。
3. **`window.cc.UIOpacity` 在 web-desktop 产物里不存在**（2026-09-23 实测，驱动器 `hud` 的 `engine` 自检列报
   `UIOpacity:false`，而 `Label`/`Graphics`/`Sprite` 都在）。后果：按类取组件返回 null；按名
   `getComponent("UIOpacity")` 也取不到（类名被压成 `e`）。**明度通道**（禁用态 78% 那一列）因此只能
   靠"对组件列表按有没有数值型 `opacity` 字段做鸭子类型"来读——驱动器 `opacityOf` 已按
   「按类 → 按名 → 鸭子类型」三档降级实现，取不到一律报 `null` 而**不报默认值 255**。
   ⚠️ 教训：早先只写第一档并把 null 兜底成 255，等于把禁用态的 78% **假验**了一遍——
   取证通道里任何"读不到"都必须显式露出来，不许兜底成"正常值"。

## 9.5 风险与已知的不安点

1. **`Mall.scene` 又要手改**：即使只加 3 个空容器，也得走「改完出一次包验证导入不报错」这条固定流程（`agents.md`）。选 P-1 甲时这个面已经压到最小。
2. **P1-4 的老问题会在弹窗上放大**：`mutate` 先 `accrue` 后 `apply`，同一条 Prepare/Upgrade 响应里 `unitPrice` 是**新价**、客人按**旧价**入账。M05 靠「单价取上一份快照」绕过；详情/升级弹窗是**常驻展示**，必须按验收第 4 条实测对账，不能沿用「下一轮自愈」的说法。
3. **满铺进度的「再开放 K 个」是纯计数**，但「该层单客收益 +1」里的 `+1` 只能来自 `config.fullFloorBonus` 的显示值。这条边界若被写成客户端常量，就是直接违反 ADR 0001。
4. **`todayEarned` 删档**会让 M05 已记录的实测读数（`— / —`、`2/35`、`+6`）在新档上重现一次，需要重跑取证确认没被本模块改坏（回归验证）。
5. **设计稿的字体现是系统字体占位**，正式字体未子集化 ⇒ 逐屏对稿时「字号一致」只能按 px 判，字形观感不作为判据（稿自己的「待办依赖」也是这么写的）。
