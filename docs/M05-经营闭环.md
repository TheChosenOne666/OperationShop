## 2. 已裁定的三项决策（2026-09-21 主理人拍板）

| # | 决策 | 理由 | 被否方案 |
| --- | --- | --- | --- |
| D1 | **开店入口做在主界面**：点 S2「待开业」铺位直接 `prepare`，无确认弹窗 | 开店不花金币、幂等（`系统-经营与成长` §2.4），没有需要确认的代价；M05 验收第 1 条要能自证。设计稿里的正式入口（`02-经营页.html` 金色「开业」按钮）留给 M06 | ①推到 M06（验收第 1 条只能靠 curl 拼证据）②M05 顺带做经营页（越界，违反模块边界原则） |
| D2 | **逐店到店数由客户端 diff `shops[].visitors` 得出**，不改服务端契约 | 已核实 `visitors` 是**开业以来历史累计、跨业务日不清零**（唯一写入点 `internal/game/service.go:530`，跨日刷新只动 `BusinessDay/CapFrozen/DailyVisitorCap/VisitorsRemaining/LastAccrualAt`），故 diff 恒为非负且跨日成立。只读服务端字段、不含任何规则常量 | 服务端 `Result` 增逐店明细：要改 Go + 单测 + B4.1/§6.1 契约文档，且**回前台走 `GET /api/v1/mall` 那条路径仍拿不到明细、diff 照样得写**，等于两边都做 |
| D3 | **Guest 不落 `.prefab` 资产**，客人节点由代码在 `GuestLayer` 下创建 | 与 M04 现有做法一致（场景只留结构、素材全走代码按路径取），可脚本化复现、零 GUI 依赖 | ①手写 `Guest.prefab`（`PrefabInfo`/`fileId` 比 `.scene` 更易错，M04 已因手写场景的重复组件引用踩过 `Error 5000`）②开一次编辑器 GUI 建（需要人在场，本轮无法无头完成） |

⚠️ D2 是对 ADR 0001「客户端不做任何数值推导」的一次**口径解释**：diff 两个服务端累计计数得出"本轮某店到了几位客人"，不涉及任何规则常量与公式（§6.2 四条红线均未触碰）。**须在 ADR 0001 追加一条注解登记此解释**，否则独立复核会判为越线。列入 §9 待裁定。

⚠️ D3 与 M04 待办里「M05 要动态实例化客人，绕不过预制体」这句判断相反，收口时要回写 `docs/M04-客户端工程与主界面.md` §6。

## 3. 架构设计

### 3.1 分层（新加粗体）

```
ApiClient.ts        传输层：带令牌发请求、抛稳定错误码（+ prepareShop）
MallStore.ts        编排层【纯 TS，零 cc 依赖 → 可用 Node 探针直测】
                      · 请求串行队列（任何时刻最多一个在飞）
                      · revision 单调守卫（丢弃过期/回退响应）
                      · 逐店 arrivals diff
                      · 暂停/恢复语义（不含定时器，由 MallScene 驱动）
MallScene.ts        接线层：5 秒节拍、前后台事件、铺位点击、幂等渲染
GuestStage.ts       表演层：客人走位 + 三视图 + 金币飘字（依赖 cc）
NumberRoll.ts       补间层：Label 数字滚动 ≤400ms ease-out（依赖 cc）
```

**为什么把编排层单独抽出来且不依赖 cc**：M05 最容易出错的是竞态与数值回退（验收第 3 条），不是画面。把它写成不 import `cc` 的纯 TS，就能用 Node 24 的类型擦除直接跑断言探针（已实测 `node --experimental-strip-types` 可用），不必为此引入 jest 等新依赖。

### 3.2 数据流

```
每 5 秒 ──► MallStore.tick() ──► 队列空？──否──► 跳过本轮（不排队、不积压）
                                   │是
                                   ▼
                       POST /api/v1/mall/settle
                                   ▼
              revision > 已应用？──否──► 丢弃（防回退，验收第 3 条）
                                   │是
                                   ▼
     diffArrivals(上一份快照, 本次快照) → [{shopId, visitors}]
                                   ▼
        ┌──────────────────────────┼──────────────────────────┐
        ▼                          ▼                          ▼
  HUD 数字滚动到               每位客人一个                铺位三态与
  state.coins /              GuestStage.spawn()           Tag 幂等重渲染
  visitorsServed             （走位→停留→飘字→淡出）
```

开店点击走同一条队列：`MallScene` 收到 S2 铺位的 `TOUCH_END` → `store.prepare(shopId)` 入队 → 队列天然串行，与轮询不会交错。

### 3.3 竞态与失败恢复（四项检查）

| 检查项 | 处理 |
| --- | --- |
| **并发安全** | 所有请求经单条 promise 链串行；`tick()` 在队列非空时**跳过本轮**而不是排队，避免请求积压后集中结算。开店与轮询不会交错 |
| **失败恢复** | 请求失败（`NETWORK`/`TIMEOUT`/`409`）→ 不更新基线快照、不打断节拍，下一轮照常；错误码进控制台日志并在 HUD 上以 `读取失败 <code>` 呈现（沿用 M04 `showError` 口径）。**连续失败不清空界面**，界面保留最后一次成功值 |
| **日志可观测** | 统一 `[m05]` 前缀，关键节点各一条：轮询发起/跳过原因、响应 `revision` 与 `changed`、逐店 arrivals、丢弃过期响应、开店成功/失败码、前后台切换、客人生成数与降级截断数 |
| **权限与边界** | 不新增任何上报字段，写命令仍只发 `{}`（`readEmptyCommand` 会拒非空体）；不引入新的网络端点；令牌仍走构建期注入的 `BuildConfig`，不落仓库 |

### 3.4 表现层细节

**客人（`GuestStage`）**

- 生成位置：`GuestLayer` 左外侧 `x = -(375 + 64)`，`y = 0`（`GuestLayer` 已在场景中，位于 `Canvas` 下 `(0,-455)`，尺寸 750×104）。
- 目标位置：**运行时坐标转换**，不硬编码。取目标铺位节点的世界坐标，用 `GuestLayer` 的 `UITransform.convertToNodeSpaceAR()` 转本地。二层铺位（`f2-*`，Floor2 下 y=336.5）转换后落在 GuestLayer 本地坐标的上方——无 Mask 不裁剪，可正常绘制。
- 位移：一段直线 `tween`（依据「v1 客人只做整体位移」），不画路径、不走楼梯。
- 三视图：水平移动段用 `chr_guest_a_side`（朝向靠 `scale.x` 正负翻转）→ 到达切 `chr_guest_a_front` → 停留 0.5 秒 → 飘字 → 切 `chr_guest_a_back` → 淡出 0.3 秒 → `destroy()`。三张图都用到，符合 §7.4「Bundle 目录里只放会被引用的素材」。
- 尺寸：显示 64×96（`美术圣经` 第 391–395 行），源图 256×256 → **`Sprite.sizeMode` 必须设 `CUSTOM`**，否则按源图尺寸显示（实现坑，先记下）。
- 三张 `SpriteFrame` 在场景启动时一次性预加载后传给 `GuestStage`，不在每次生成时异步取。

**金币飘字**

- 位置：目标店铺节点处；内容 `ico_coin`（48×48）+ 文案 **`+{shops[].unitPrice}`**（服务端返回的该店单客收益，已含满铺加成，**不做乘法**）。一位客人一次飘字。
- 动画：向上位移约 60px + 淡出，结束销毁。
- ⚠️ 文案格式文档无规定（`美术圣经` 只规定了图标用途），列入 §9 待裁定。

**数字滚动（`NumberRoll`）**

- `tween` 一个中间对象的数值，`onUpdate` 写 `Label.string`；时长 **400ms**、`Easing.Quadratic.Out`（`美术圣经` 第 848 行上限）。
- 中途来新目标：`Tween.stopAllByTarget` 后从**当前显示值**起滚，保证不回退、不跳变。

**大额补算降级（回前台后 diff 可能几十位）**

- 单轮最多生成 **5** 位客人，超出部分不生成；**金币与客流数字仍按服务端值滚动到位**——即"表现降级、数值不降级"，对齐 `开发规划文档` §M05 风险条「把表现对齐到服务端返回的到店数」。
- 截断时打一条日志写明本轮实际到店数与生成数。阈值 5 为常量，列入 §9 待裁定。

**铺位点击的可用态**

| 铺位状态 | 点击行为 |
| --- | --- |
| S1 未开放 | 无反应 + 一条日志（解锁入口属 M06 布局页，本模块不做提示 UI） |
| S2 待开业 | `POST /api/v1/shops/{shopId}/prepare` → 成功后重渲染为 S3 |
| S3 营业中 | 无反应 + 一条日志（店铺详情弹窗属 M06） |

## 8. 验证计划

1. **Go 回归**：`go test ./...`（本模块不改 Go，跑一遍证明没碰坏）。
2. **逻辑探针**：`node --experimental-strip-types tools/m05_probe.ts`，用假 transport 断言五件事——逐店 diff 正确（含一轮多店、含 0 到店）、`revision` 更小或相等的响应被丢弃、请求串行不并发、暂停期间不发请求、恢复时立即拉一次快照。
3. **端到端**（web-desktop 构建 + 本地后端 + chrome-devtools MCP 全页截图）：
   - ① 初始态：一层两铺「待开业」、金币 1280、客流 `0/—`
   - ② 点 `f1-s1` → 铺位切咖啡立绘、Tag 变店名（S3）
   - ③ 5 秒内客人从左外侧走到咖啡门口 + 金币飘字 + HUD 金币滚动、客流分母冻结出现
   - ④ 只开一家店时，`f1-s2`（花束，未开业）始终不出客人
   - ⑤ 刷新页面 → 数值与店铺开关状态与刷新前一致
   - ⑥ 控制台无 `Error`/`Missing class`，`[m05]` 日志完整
4. **切后台/回前台**：web 平台 `EVENT_HIDE` **引擎文档明写不保证触发**（`cc.d.ts` 第 28005 行），故 web 侧只能取证 `pause()`/`resume()` 的行为（探针覆盖 + 控制台手工触发）；**正式结案需在微信开发者工具或真机复验**，登记为 M05 遗留项。
5. **包体报数**：`python tools/m04_build.py --size-only`。

### 11.3 实测发现的事实与坑（都付过学费，别再踩）

1. **Cocos 3.8 的 `Sprite` 没有 `flipX`**（那是 2.x 的 API）。能翻的是 `SpriteFrame.flipUVX`，而它挂在**资产**上——一改就把所有共用该帧的客人全翻。逐节点翻转只能用负 `scale`。
2. **web-desktop 构建的点击坐标必须以 canvas 元素中心为原点**。`FIXED_HEIGHT` 把高度锁死、宽度按窗口比例外扩，Canvas 节点始终居中；按左边缘算会整体平移几百像素、点到场景之外。实测第一版就是这么算的，DOM 收到了 touch 事件但游戏毫无反应——**"事件没送到"和"送错了地方"在日志上长得一样**，故驱动器加了 `probe` 步骤回报事件计数与 canvas 矩形。
3. **错误横幅不能只靠"下一次成功更新"来清**。空闲 settle 会被 revision 守卫丢弃、根本不触发 `onStoreUpdate`；当日客流耗尽后再也不会有成功更新，错误就永久卡在招牌上。改为挂 3 秒定时自清。实测杀后端后连拍 70 帧，第 52 帧起在「招牌原文」与「连接中断 NETWORK」之间按 5 秒节拍交替。
4. **`Component._onPreDestroy()` 在 `onDestroy` 之前就已 `unscheduleAllCallbacks()`**（`scene-graph/component.ts:407`）。所以 `onDestroy` 里再 `this.unschedule(...)` 是多余的；真正需要手动清的是 `game.on` 的监听（挂在 game 这个 EventTarget 上，与节点无关）和挂在 Node/UIOpacity/中间态对象上的补间（走 ActionManager）。
5. **`VAR=x cmd1 && cmd2` 里变量只作用于 `cmd1`**。第一次起后端就是这么失败的：`MALL_LISTEN_ADDR=… go build … && ./streetcorner.exe` 让服务端拿不到环境变量直接退出。要么 `export`，要么放进子 shell。
6. **后端在启动阶段不可达时，本模块不重试**：`fetchConfig()` 失败会让 `start()` 整体走 `onFatal`，轮询压根不启动，界面停在「读取失败 NETWORK」直到重开游戏。M04 就是这个行为，M05 未改（不在交付物内）。**真机上线前这是一条要处理的体验问题**，已登记进 §11.6 遗留。
