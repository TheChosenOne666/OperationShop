## 2. 四条验收逐条判定

### #1 开店后能看到第一位客人到店，金币增加、已到店 +1、`visitorsRemaining` −1 —— **实质达成；字面「5 秒内」不可达（P2-A）**

真实 HTTP（冷启动新档，`tools/review-m05-http.mjs`，两次独立跑）：

```

2-b PASS 开店本身不产收益（首次开店以准备时刻起算） used=0 earned=0
2-c PASS 开店后上限仍未冻结                     dailyVisitorCap=null

真实浏览器（读运行时节点，非截图推断）：

```

**为什么「5 秒内」不可能成立**：服务端 `visitorIntervalSeconds = 5`，首次开店把结算游标锚定在**点击那一刻**（`service.go:279-283`，实测 2-b 成立），所以第一位客人在服务端侧**最早也只能在 T0+5s 存在**；客户端轮询相位再加 0–5s；`GuestStage` 的走位 1.6s + 停留 0.5s 再加 2.1s 才是"看见人站在门口"。实测落点区间 **5.1s – 10s**，飘字出现在 **7.2s – 12.1s**。
→ 这条不是实现缺陷，是**判据写错了单位**（把服务端节拍写成了玩家可见延迟）。取向建议见 §6。

### #4 未开业的铺位不产生收益，也不消耗客流 —— **PASS**

- 真实 HTTP：只开咖啡时连续三轮，`flowers.visitors` 恒 0、`flowers.revenue` 恒 0、`flowers.unitPrice` 恒 9（等级价，无满铺加成）→ 3-a / 3-b PASS。
- 客流消耗侧：`dailyVisitorCap` 在只有咖啡开业时冻结为 **35**（=20+15×1），中途开第二家店**不补当日客流**；而两店在同一天首次到店前就都开业时冻结为 **50**（实测 reload 后 HUD `3/50`）。两条都与 GDD §5.3 一致 → 未开业店既没进账也没从池子里扣。
- 这条的**权威保障在服务端**：`accrue` 的轮转显式跳过未开业店（`service.go:513-516`），并由 Go 测试钉死——`TestServiceUnpreparedShopsDoNotAccrue`、`TestServiceRoundRobinSkipsUnprepared`、`TestServiceUnpreparedAcrossDays`（本次随 `go test -race` 全绿）。
- 客户端这一半：真实响应回放 R7 显示未开业店从未被画上人。
- ⚠️ 口径纠正：`tools/m05_probe.ts` ⑦ 那条用例名（"只有 visitors 变动的店才会出客人"）**不能算这条验收的证据**，理由见 §4.1。真正的证据是上面这三项。

## 3. 三处独立判断

### 3a `git show 84b2fa6` 做对了吗？—— **三处修复本身成立；夹具问题只解决了一半，声明收窄是主要收益**

**修复本身（我逐行读代码，不读它的自我陈述）：**

| 项 | 判定 | 依据 |
| --- | --- | --- |
| P1-1 串行链被一次异常永久投毒 | **成立** | `MallStore.ts:213` 存链的那份改为 `run.catch(() => undefined)`，任务体在 `try/catch/finally` 内，`inFlight` 必减；`accept` 里 observer 调用**先于** `this.applied = view`（`:257-263`），渲染抛异常时基线不前移、下一轮会把这批到店补上。我另查到一条残留：`run` 自身仍可能 reject（唯一路径是 `onStoreError` 自己抛），而 `tick()` 用 `void this.enqueue(...)` 丢弃返回值 → 那一次会是 unhandled rejection。`MallScene.onStoreError` 有 `isValid` 与 null 守卫，当前不可达，记 P2-G 不计缺陷 |
| P1-2 守卫只看 revision 会永久冻结界面 | **成立且方向正确** | `passesGuard`（`:227-239`）把「指纹变 或 revision 变小」判为基线作废并当首帧重新应用。旧版把这条真实故障写成了期望值（"金币保持 1500"）。改后我不认为它引入了新暴露面：代码注释声称"严格串行不存在乱序响应"，我核对 `enqueue` 的链式串接与 `tick()` 的 busy 跳过，这条声称成立 |
| 死代码清理（`diffArrivals` 的未知店铺 warn） | **同意** | 同一会话内店铺清单由配置固定、改配置必然改指纹 → 该分支不可达；与 §八-10 去 `validateSlots` 冗余校验是同一个判断 |

**夹具问题（判据：凡是断言「某状态不会发生」的用例，检查夹具是否主动排除了它发生的可能）：**

改对了的部分：`view()` 现在接受显式的 `prepared` 集合，⑥ 里加了「开局两家都未开业」的断言，⑦ 改名并写清了探针证不了服务端不变量。

**但问题的根没有消除**：`diffArrivals` 与 `MallStore` **根本不读 `prepared` 字段**（全文件只读 `shops[].visitors`、`revision`、`rulesFingerprint`、`visitorsServed`、`dailyVisitorCap`）。所以无论夹具把 `prepared` 写成什么，⑥⑦ 关于"开店""未开业不出客人"的断言都**不可能失败**——84b2fa6 加强的是夹具的**表达力**，不是断言的**效力**。逐条点名：

1. ⑦ 的 `assert.ok(all.every(a => a.shopId !== "flowers"))`：夹具里 `flowers.visitors` 恒为 0 → 仍是断言自己造的假数据。**同类形态残留的一条就是它。**
2. ⑥ 的 `assert.strictEqual(...shops.find(id==="coffee").prepared, true)`：回显 `view(..., ["coffee"])` 的输入。
3. ① 的「0 到店（空闲轮询）→ 空数组」：纯函数测试，输入即断言对象，可接受。
4. 新引入的反向形态：②「基线作废」用例手工把 `rebuilt.rulesFingerprint` 改成与基线不同来制造条件。真实场景里指纹变化必然伴随服务端拒旧档 + 整页重载，**同一会话内是否可达，探针既没证也没声称证**。风险低，但记一笔。

**我的替代做法**：不修它的夹具，而是换数据源——`tools/review-m05-replay.ts` 把 §2 抓到的 **33 条真实响应**原序喂进同一个被测 `MallStore`，R1–R7 由我按规格自写。结果 6/7，唯一 FAIL 的 R6 正是 §3c。**这条 FAIL 是夹具类探针在原理上抓不到的**：假数据里没有"服务端在同一响应里换了单价"这个事实。

### 3b 客户端在 ADR 0001 下是否越线 —— **未越线（就三条硬契约与 §6.2 四条红线而言）；但紧邻红线处有一处真推导，即 §3c**

先把事实钉住（全部实测/自查，不引文档说法）：

| 契约 | 实测 |
| --- | --- |
| ① 命令体只接受空 JSON | 我发 `{"coins":5}` → `400 INVALID_COMMAND`；`ApiClient.ts:49` 恒发 `{}` |
| ② 时间由服务端推进 | `grep Date.now\|new Date\|performance.now\|setTimeout` 在 `scripts/*.ts` 生产代码 **0 命中**；轮询间隔取 `config.visitorIntervalSeconds`（`MallScene.ts:112`） |
| ③ 只据服务端返回值播动画 | **这一条有偏差，见下** |
| §6.2 不自行算分母 / 不判加成 | `grep baseVisitors\|visitorsPerShop\|fullFloorBonus\|levelCoinsPerVisitor\|upgradeCosts` 在 `scripts/*.ts`（除 `ApiTypes.ts` 的类型镜像）**0 命中**；HUD 分母直接取 `dailyVisitorCap`，`null` 时显示 `—`（`MallScene.ts:429`，实测 `0/—`） |

**关于「对累计计数做差算不算数值推导」——我判：不算。** 理由与 ADR 追加的那段口径澄清一致，且我独立核对了它依赖的事实：`shops[].visitors` 的唯一写入点确实在 `accrue` 的 `shop.Visitors++`（`service.go:530`），跨业务日刷新只动 `BusinessDay/CapFrozen/DailyVisitorCap/VisitorsRemaining/LastAccrualAt`（`service.go:481-489`，实测存档 diff 印证），所以差值恒非负、跨日成立。它不含规则常量、不预测未发生量、且与 `Result.visitorsUsed` 交叉校验、不一致时出声并以服务端为准。这是**映射**，不是推导。

**但同一批代码里有一处真正的推导**：`GuestStage.ts:81` 把「本次响应里的 `shop.unitPrice`」当作「本轮每位客人的实付额」，`:182` 直接把它写成飘字文本。服务端从没给过"每位客人实付多少"这个量，这是客户端补出来的一个推断，而且**这个推断是错的**（§3c）。ADR 0001 第 3 条的原文是"客户端只负责据此播放补间动画，不做任何数值推导"——越的不是"零计算"的算术线，而是"据服务端给的量播动画"这条线：**动画里出现的金额不是服务端给的。**

对那条 2026-09-21 追加进 ADR 的口径澄清，我的独立评价：**它本身站得住**（限定得很清楚，只覆盖不含规则常量的累计计数做差），但它**没有覆盖飘字金额**；如果按同一逻辑给飘字也开一张豁免，红线就没有边界了。所以：澄清保留，飘字按实现缺陷算。
⚠️ 程序上的意见：这条澄清是 M05 期间由实现侧写进 ADR 的，判据与被判对象同源。它改的是**全模块生效的架构口径**（ADR 0001 自己写着"决策范围：全部模块，M02/M06/M07 不得回退"），这类改动应走主理人裁定后再入库，不宜作为模块收尾的附带项。

### 3c 表现层显示的到店收益与后端实际入账是否可能不一致 —— **成立，已三次复现（含运行时文本与截图）**

**机理（读 `internal/game/service.go` 确定）**：`mutate` 的顺序是 **先 `accrue` 后 `apply`**（`:436-441`），而 `view()` 在 `apply` 之后才取 `unitPrice`（`:675`）；`unitPrice` = 等级价 + `floorFull` 加成（`:398-404`）。因此**同一条 Prepare（或 Upgrade）响应里**，本轮客人是按**旧价**入账的，`state.shops[].unitPrice` 却是**新价**。价格只可能因 `Prepare`/`Upgrade` 变化（`Unlock` 不改 `prepared`/`level`，`floorFull` 要求"已解锁且已开业"，而未解锁铺位的店不可能已开业），所以这个偏差**恰好锁定在带客人的写命令响应上**。

**证据一 · 真实 HTTP**（`review-m05-http.mjs` 第 4 阶段，制造一位待结算客人后开第二家店）：
```
before coins=1304 coffee@6 → prepare flowers: used=1 earned=6
after  coins=1310 coffee@7 flowers@10
FAIL 4-a 本轮客人实付单价 == 响应内该店 unitPrice → 实付 6/位，响应里 coffee.unitPrice=7
```

**证据二 · 服务端分段账自证**（同一份存档，`GET` 不落盘，直接读盘）：
```json
"coffee": {"visitors":9,"revenue":54,
           "segments":[{"unitPrice":6,"visitors":9,"revenue":54},
                       {"unitPrice":7,"visitors":0,"revenue":0}]}
```
7 价段 **0 位客人**——服务端明确记账"这 9 位全是 6 价"。而 `TestPrepareTriggeringFullFloorAddsSingleBonusSegment`（`service_test.go:1158`）正是为这个语义写的：旧段单价不变、新段直接是 bonus 价。**服务端是对的，且有测试钉着。**

**证据三 · 真实浏览器运行时文本**（`review-m05-drive2.mjs`，后台停轮询 20s 后开第二家店）：
```
[m05] 应用 prepare 响应 revision=4 changed=true 金币=1310 已到店=5 本轮到店=4
运行时 GuestLayer 子节点：4 个 Guest（2 个已在门口 -180,76，2 个在路上）
CoinFloat 的 Label 文本：["+7"] → ["+7","+7"] → ["+7","+7"]
截图 web6/50-float-a.png：咖啡铺门口两位客人 + 金币图标 + "+7"，HUD 1310 / 5/35
```
→ 界面显示 4 位客人各付 **7**（合计 28），服务端入账 **24**（1286→1310，4×6）。**HUD 总额、存档、账目全对；错的是那 0.8 秒的飘字。**

**触发概率**：稳态轮询下约 40–50%（我三次浏览器尝试：web2 一次命中、web4/web5 各 0 位）。原因是客户端轮询周期与服务端到店周期同为 5s 时相位会互相咬住；**一旦两者错开就稳定命中**——而错开是常态：重进游戏后轮询时钟从加载时刻重启，服务端游标却是跨会话延续的（web2 正是这个场景）。后台停轮询更会把待结算人数堆到 4–11 位（web6/web8 实测）。

**严重度与是否阻塞——我的判断：P1，不阻塞 M05 放行。**
- 不阻塞的理由：M05 四条验收的观测点全是 HUD 数值与存档状态，飘字金额不在任何一条判据里；服务端权威没被破坏（金币、账目、客流全对），玩家无法据此多拿一分钱。
- 但不能拖的理由：它错在"钱"上，且 `unitPrice` 在 GDD §6.1 里的**规定用途就是店铺详情弹窗展示"单客收益构成"**——M06 一上线，同一个误用会从"0.8 秒的飘字"变成"常驻的错误单价"，那时它是 P0 级。

## 4. 探针与驱动器审查（写验同源判定）

### 4.1 `tools/m05_probe.ts`（编排层夹具探针）

我今天自己跑的：**19/19 通过**（不采信其头部注释的声明，但结论一致）。

定性：它是**合格的编排层单测**，覆盖 diff / 守卫 / 串行 / 前后台 / 交叉校验 / 失败恢复，夹具注入的异常与竞态都是真代码路径。**它不是任何一条 M05 验收标准的证据**，因为它跑的是假 transport，从未接触 HTTP、引擎、渲染。

写验同源判定：**⑥⑦ 两条按"验证收"处理**——用例名（"开店 → 下一轮结算 → 一位客人归属该店、金币增加、已到店 +1"、"未开业铺位不出客人"）与验收 1/4 逐字同名，内容却只是编排层对假数据的回显。84b2fa6 已在注释里自认这点，但**用例名没改**：只看名字的人会把"验收 1 通过"记在它身上。→ P2-B（改名或加"本用例不证验收 N"前缀）。

### 4.2 `tools/m05_web_drive.mjs`（web 端到端驱动器）

先说公道话：它**不含任何验收判据**——只截图、收控制台、统计未捕获异常，判断留给人读图。所以它不构成"探针的判据与规格不一致"那种写验同源。它的注释结论我没读，也不影响这个判断。

但审查中实测出两条硬伤：

**P1-B 视口与画布宽度不匹配，导致部分铺位物理上点不到。**
它把视口仿真成 750×1334（`m05_web_drive.mjs:140-142`），而构建产物的画布是 **1280 CSS 宽**（实测 `getBoundingClientRect` = 1280×960 @ (5,86)，`GameDiv` 在 `index.html` 里写死 1280×960，`Emulation.setDeviceMetricsOverride` 没能让它跟着视口缩）。它的坐标换算本身是对的（以画布中心为原点、`scale = rect.h/1334 = 0.72`），于是设计坐标 x>146 的触点算出的 CSS x 会超过 750，**落在视口之外被浏览器丢弃**。
实测：我用它的 `click` 点 `f1-s2`(220.5) 与再点一次，**客户端控制台一行日志都没有**（`onSlotTouched` 无论走哪个分支都必打日志）→ 事件根本没送到引擎。同一坐标在我自写的 `review-m05-drive2.mjs`（视口 1280×1400）下正常触发 `玩家请求开店：flowers`。
影响面：受影响的节点是 `f1-s2`、`f2-s2`(0)、`f2-s3`(239) 等一切 x>146 的铺位。也就是说**这条驱动器产不出"开第二家店"的证据**；谁用它复验 M05/M06 的多铺位交互，都会得到"点了没反应"的假阴性。这也解释了为什么它自带的示例步骤只点 `f1-s1`。

**P2-E `burst` 的"PNG 字节数变化 ≈ 数字变了"不能归因。**
同一帧里客人位移、飘字淡出都会改字节数。实测 `12-walk` 连拍 16 张，变化帧号 1,2,3,4,5,8,9,10,11,12,15 —— 这些全是走位动画造成的，与 HUD 数字无关。用它来证明"补间中间帧被抓到"是**弱判据**。我改用 `evalfile` 直接读 `Hud/CoinLabel` 的 `string`，才拿到可归因的显示值。

**我的替代工具**：`tools/review-m05-drive2.mjs`（视口 1280×1400 + `evalfile` 步骤，读运行时 Label 与 GuestLayer 子节点）。§2、§3 里所有"界面显示的是什么"的结论都出自它。

## 6. 该改规格 vs 该改实现（只给取向）

### 该改规格

1. **验收 #1 的「5 秒内」**（P2-A）——把"服务端节拍"与"玩家可见延迟"分开写。取向：改成「开店后**第一个结算周期内**服务端产生第一位客人，界面在**下一次轮询**即反映（金币与已到店各 +1），客人走位在 B3.5 的 1.6s+0.5s 内完成」，并给实测落点区间 5.1–10s。
2. **B3.6「回前台立即拉一次快照」**（P2-C）——实测证明按字面拉 `GET /api/v1/mall` 达不到该条括注自己声明的目的（"服务端会把这段时间的客流算出来"），因为 `Snapshot()` 明确不结算。取向：**改规格认可 settle 的实现**，同时补一句约束：回前台的这一次请求会推进服务端状态、可能落盘，因此不得被实现成"心跳"或高频触发。
3. **`unitPrice` 的用途边界**（P1-A 的根）——GDD §6.1 现在只写"用于店铺详情弹窗展示构成（可选派生）"，没说它**不能**当"每位客人实付额"用。取向：在 §6.1 明确 `unitPrice` 是「该店**当前**的单客收益档位」，与"本轮客人按什么价入账"不是同一件事；后者若表现层要用，必须由服务端在 `Result` 里给逐店明细。
4. **飘字金额的验收观测点缺失**——M05 四条验收没有任何一条覆盖"表现层显示的金额"，所以 P1-A 从判据上漏网。取向：M05 措辞不动，但把这条补进 M06 的验收（详情弹窗一出现 `unitPrice`，它就是常驻招牌）。

### 该改实现

1. **P1-A（首选，一行）**：飘字取**上一份已应用快照**里该店的 `unitPrice`（本轮客人入账时的价），而不是本次响应的价。基线作废的首帧不做差、也就不出飘字，与现有 `diffArrivals` 的降级策略天然一致。不推荐改服务端契约（加逐店明细）作为 M05 的收口手段——那会牵动 `Result` 结构与存档无关字段，属 M06/M07 量级的变更。
2. **P1-B**：把驱动器的视口给成不小于画布宽度（或先把 `GameDiv`/canvas 适配到视口再算坐标），并在 `click` 步骤里**断言事件送达**（例如点击后控制台必出现对应日志，否则报 FAIL）。现在的失败模式是静默的——这是它最危险的地方。
3. **P2-B**：探针 ⑥⑦ 改名，去掉与验收条号同名的表述；或在名字里显式标注"（仅编排层，不证验收 N）"。
4. **P2-D**：`ApiClient.ts:56` 的注释改回真实用途（`fetchMall` 现在只在启动首帧调用）。
5. **P2-G**：`tick()` / `resume()` 丢弃的 `run` 补一道 `.catch` 记日志，别把"渲染层抛异常"变成静默的 unhandled rejection。
