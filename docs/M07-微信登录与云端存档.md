## 1. 这一模块解决什么

| 痛点 | 现状证据 | 后果 |
| --- | --- | --- |
| 请求鉴权是一个写进构建产物的开发令牌 | `ApiClient.ts` 每个请求带 `Bearer ${BUILD_CONFIG.devToken}`（`BuildConfig.ts` 由构建脚本生成、已 gitignore，但值随产物分发） | 令牌即公开口令；任何拿到构建产物的人都能读写存档，这不是「登录」 |
| 服务端强制仅本机访问，且只有一个账号一份存档 | `handler.go` 回环校验（`LOCAL_ONLY`）；`MALL_DATA_PATH` 单文件；启动强制 `MALL_LISTEN_ADDR` 为回环 IP | 换设备/清缓存后数据不跟人走；服务器无法部署到公网，真实玩家进不来 |
| 会话没有过期与续期机制 | 无会话概念，开发令牌永不过期 | 上线检查清单「会话令牌具备过期与续期机制」无从勾选 |
| 每店分段数 ≤6 只是实现逻辑保证，不是加载校验（`P2-B` 转入的前置） | `validateState` 实测接受一份 20 段但逐段恒等式自洽的存档 | 本模块开始按账号接收存档后，「用任意分段数构造合法账目」的面被放开 |

## 2. 使用场景（玩家路径）

1. **首次进入**：打开小游戏 → 微信登录 → 建立会话 → 新账号拿到初始存档（一层两店可开业、初始金币与服务端规则一致）。
2. **换设备 / 清缓存**：同一微信账号进入 → 登录 → 读到服务端上属于该账号的那份存档，金币、客流、店铺状态、等级完全一致（需求文档 §4.7「换设备后以服务端数据为准」）。
3. **会话过期**：令牌到期后客户端自动重新登录，玩家无感；重登期间界面不丢已显示的数值。
4. **开发期联调**：本机开发仍走开发令牌 + 回环，M04–M06 的取证配方（真实进程 + 真实 HTTP + web-desktop 驱动器）不加改动继续可用。

## 3. 需求点

| # | 需求 | 要点 |
| --- | --- | --- |
| R1 | **微信登录换会话** | 客户端拿登录凭证 `code` → `POST /api/v1/session/wechat` 入参只收 `{ code }` → 服务端用 `code` 换账号标识 → 签发本服务的会话令牌（带过期时间）返回。**不接受客户端声明的任何身份**（昵称、openid、头像一律不收） |
| R2 | **会话鉴权** | 登录后的全部 `/api/v1/*` 请求带会话令牌；无票 / 过期 / 伪造 → 401 + 稳定错误码（过期与无效分开），提示不泄露细节。`/healthz` 保持免票 |
| R3 | **自动重登** | 客户端收到「会话过期」码 → 自动重新登录 → 把刚才失败的请求**重放一次**；仍失败才把可读错误抛给玩家，且界面保留最后一次成功值（沿用 M05 验收第 3 条口径） |
| R4 | **账号级存档** | 一个微信账号一份存档，按账号隔离；同一账号的并发写不重复结算、不重复扣费（复用 M02 已有的互斥与幂等语义，验收 #2 的实现层保证不回退） |
| R5 | **不毁档底线不变** | 存档损坏 / 规则版本不匹配时：拒绝加载、保留原文件、明确暴露，**不得静默清零**（需求文档 §4.7；M01 起的行为不因登录改造改变） |
| R6 | **分段数上界升格为加载校验**（`P2-B` 转入的前置） | 每店 `segments` 数量 ≤6 成为存档加载的硬校验：越界即判存档损坏、拒绝加载。同期复核 GDD §5.5 其余校验项在「外部账号存档」场景下的强度，发现缺口一并登记 |
| R7 | **开发 / 生产双模开关** | 本地开发令牌与「仅本机访问」从硬编码改为模式开关：**开发态**保持现状（联调取证零改动）；**生产态**关闭回环限制与开发令牌，监听地址走配置。当前模式在启动日志与 `/healthz` 可见 |
| R8 | **日志与隐私** | 登录、签发、拒绝有可追踪日志；**不记录 `code`、账号标识原文、令牌**（需求文档 §七：不落盘昵称头像等敏感字段；M01 起「日志不记令牌与查询参数」的底线不破） |

## 4. 验收标准

> 对应规划文档 §三 M07 三条 + `P2-B` 前置 + 项目质量门。每条都要有可取证的实际读数，不接受"应该没问题"。

1. **换设备一致**：同一微信账号在新会话（清凭证 / 新设备）进入后，金币、客流、店铺状态与等级与服务端存档逐字段一致。
2. **并发不重复**：同一账号并发发写命令（结算 / 开店 / 解锁 / 升级），不重复结算、不重复扣费；账目恒等式 `coins == initialCoins + Σrevenue − spent` 仍成立。
3. **过期自动重登**：会话过期后客户端自动重新登录并重放请求，数据不丢；重登失败时有可读提示，界面数值保留最后一次成功值。
4. **分段上界（`P2-B`）**：构造一份每店 7 段（逐段恒等式自洽）的存档 → 拒绝加载且原文件保留；每店 6 段的合法存档正常加载。
5. **开发态回归**：M04–M06 的取证配方（真实进程 + 真实 HTTP + web-desktop 驱动器 + 探针）**不加改动**跑通，全部维持通过。
6. **质量门**：`gofmt -l .` / `go vet ./...` / `go test -count=1 -race ./...` 全绿；新增代码有单测，覆盖正常路径 + 至少一个异常 / 边界用例。

## 5. 测试策略

| 层 | 测什么 | 怎么算测过 |
| --- | --- | --- |
| 后端单测 | 登录换会话（成功 / 对方返回错误码 / 网络失败 / 响应缺字段）；会话签发与校验（过期 / 伪造 / 篡改 / 空票）；按账号取存档（账号间隔离、同账号并发写串行）；分段 ≤6 校验（6 过 / 7 拒）；双模启动（开发态维持回环 + 开发令牌，生产态拒绝缺配置的裸奔启动） | `internal/*` 单测逐条覆盖，注入假传输 / 假时钟，不访问外网 |
| 客户端编排 | 401 过期码 → 自动重登 → 重放一次；重登再失败 → 提示且数值不动；登录令牌在内存中的生命周期 | 编排层探针（Node 直跑断言，含一条反向验证） |
| 联调 | 真实进程 + 真实 HTTP：登录 → 拿票 → 全部命令带票 → 会话过期 → 自动重登 → 重放成功；开发态回归 M04–M06 配方 | e2e 脚本读数取证 |

## 6. 明确不做

- 不接 unionid、开放数据域、好友排行榜（M08）。
- 不迁微信云开发：存档仍在自托管服务端、按账号隔离（默认决策 D-b）。
- 不部署服务器、不配域名与 HTTPS、不做防沉迷与隐私协议材料（均属 M09）。
- 不做账号合并 / 存档迁移工具（ADR 0004 既定：开发期删档重建）。
- 不改编译产物体积口径之外的新素材（本模块预期零新素材）。

## 9.2 后端改动

### a. 存档校验：分段数上界升格（PRD R6，`P2-B` 结清）

- `internal/game/service.go` 的 `validateState`：每家店 `len(Segments)` 超过上界即判存档损坏。
- 上界**不写死 6**，按配置推导：`1（开店建首段）+ len(cfg.UpgradeCosts)（升级改价，最多 4）+ 1（满铺状态变化，不可逆一次）= 6`（GDD §5.6 的推导原样落进代码注释）。当前配置下恰为 6，改配置时自动跟随（ADR 0004 精神）。
- `schemaVersion` **不变（仍 3）**：只加校验、不加字段。现有开发档最长路径恰好 6 段，不受影响；>6 段的档由「接受」变「拒绝」即本条的目的。
- 同期复核 GDD §5.5 其余校验项（`unlockedSlots` / 客流上限二态 / 账目恒等式 / 时间戳）：结论是**均为纯结构性校验、不依赖「本机自产」假设**，无需新增——复核过程写进文档，不留「据说查过」。

### b. 新包 `internal/session`：登录换票 + 会话存储

```
session.CodeExchanger  interface { Exchange(ctx, code) (accountKey string, err error) }  // code → 账号键
session.WeChatExchanger{AppID, AppSecret, Endpoint, HTTP}  // 生产：真调 jscode2session
session.DevExchanger{}                                     // 开发：code 原样派生账号键（仅 dev 模式可注入）
session.Store                                          // 进程内 map：token → {accountKey, expiresAt}
```

- **令牌**：`crypto/rand` 32 字节 → hex（256-bit）。签发即 `Store.Issue(accountKey, ttl, now)`；校验 `Store.Authenticate(token, now)` 返回 accountKey 或区分「不存在/已过期」两个错误（api 层映射 `SESSION_INVALID` / `SESSION_EXPIRED`）。
- **过期清扫**：签发时顺手扫掉过期项（账号量级小，零 goroutine、零定时器）。
- **WeChatExchanger**：`GET https://api.weixin.qq.com/sns/jscode2session?appid&secret&js_code&grant_type=authorization_code`，5s 超时；响应 `errcode != 0` → 包装错误，**errcode/errmsg 只进日志、绝不返回客户端**（错误细节不给外部）；缺 `openid` 字段同样按失败处理。
- **隐私**：`code`、`session_key`、openid 原文都不落日志；openid 只以 **sha256 截断 hex（账号键）** 形式存在——文件名、日志、内存键都用账号键，openid 原文仅在 Exchange 返回后到派生账号键之前存活。
- 单测全部注入假 HTTP（`httptest.Server` 或 RoundTripper stub）与假时钟，不访问外网。

### c. `internal/api`：双模中间件 + 新路由 + 账号服务表

- `Options` 增补：`Mode`（`dev`/`wechat`）、`Exchanger`、`Sessions *session.Store`、`SessionTTL`。按 `Mode` 分派：
  - **dev**：维持现状——loopback 强制、origin 白名单、开发令牌 ≥32 位必填；**另接受**有效会话令牌（T-3）。`MALL_DEV_TOKEN` 缺失仍拒绝启动（`TestNewHandlerRejectsInvalidOptions` 全绿不变）。
  - **wechat**：不要求开发令牌；**关闭 loopback 检查**（公网部署的前提）；origin 逻辑原样（无 Origin 放行——微信 `wx.request` 不发 Origin；有 Origin 仍查白名单）；缺 `Exchanger`/`Sessions` 拒绝启动。
- 新路由 `POST /api/v1/session/wechat`：
  - 入参 `{ "code": "..." }`：**不能**复用 `readEmptyCommand`（它只收 `{}`）——新写严格解码：`Content-Type` 必须 JSON、体 ≤1KB、恰一个对象、只许 `code` 一个非空字符串字段，其余一律 `INVALID_COMMAND`。
  - 成功 200：`{ "token": "...", "expiresInSeconds": 600 }`（不返回 openid、不返回 accountKey——客户端不需要）。
  - 失败：`WECHAT_CODE_REJECTED`（401，换票失败，细节只进日志）。
- 认证中间件统一出口：Bearer 票 → `Sessions.Authenticate` → 账号键 → `accounts.Service(key)`；开发令牌直通 → 固定单账号（`"dev"`，即现有 `MALL_DATA_PATH` 单文件语义）。
- 新文件 `internal/api/accounts.go`：`map[账号键]*game.Service` + `RWMutex`，懒加载——首见账号时 `game.NewService(cfg, FileStore{Path: dir/<sha256前32hex>.json}, now)`（无档则建新档）。**同账号并发写由每个 Service 自己的 `sync.Mutex` 串行化**（M02 的四类并发保证原样继承，验收 #2 的实现层不变）；**账号间互不阻塞**。某账号存档损坏 → 该账号请求 500 `SAVE_FAILED`，**不拖垮其他账号、不全局拒绝启动**（与单账号时代「启动即拒」不同，多账号必须逐账号隔离，登记为行为变更）。
- 新错误码（进 B4.2 稳定集合）：`SESSION_INVALID`（401，票不存在/被篡改）、`SESSION_EXPIRED`（401，票过期）、`WECHAT_CODE_REJECTED`（401，换票失败）。

### d. `cmd/server/main.go`：双模启动

- 新增环境变量：`MALL_AUTH_MODE`（`dev` 默认 / `wechat`）、`MALL_WECHAT_APPID`、`MALL_WECHAT_APPSECRET`、`MALL_SESSION_TTL`（可选，默认 600s）。
- `MALL_LISTEN_ADDR`：dev 模式维持「必须显式回环 IP」；wechat 模式放开（仍须显式 `host:port`，不允许空）。
- `MALL_DATA_PATH` 按 T-1 分语义；wechat 模式下目录不存在则建（0700）。
- 启动日志与 `/healthz` 报告当前模式（`"mode":"dev|wechat"`、`"wechatLogin":true|false`）。
- **零新第三方依赖**（全部标准库：`crypto/rand`、`crypto/sha256`、`net/http`）。

## 9.3 客户端改动（`NewProject/assets/scripts`）

## 9.5 风险与已知不安点

1. **`MALL_DATA_PATH` 语义分叉**（T-1）：dev 回归的生命线是「单文件语义逐字节不变」；联调第一步就必须先跑通旧配方再动新代码路径。
2. **会话纯内存**（T-2）：重启全下线。客户端自动重登已兜底（R3），但**真机首次冷启动必然多一次 `wx.login` + 换票往返**，启动时长增量要在 Boot 实测里留读数。
3. **多进程部署仍不支持**：「恰好一个 Service 进程拥有一个存档文件」的单写者约束延续到每账号文件；`架构现状` §2 末「锁不跨进程」边界原样成立，多实例属 M09 议题。
4. **wechat 模式关闭 loopback 后**，安全边界全部押在「换票真伪」上：DevExchanger **只允许在 dev 模式注入**（`NewHandler` 按模式强校验），杜绝「生产环境配了假 exchanger」的类上线事故。
5. **M06 独立复核未结**：`ApiClient.ts`/`Boot.ts`/`开发规划文档.md` 是两边都要动的文件，若复核要求回改 M06 实现，本模块 diff 可能要跟着 rebase——现在改就有此风险，不改只会更晚。
