## 1. 不可测 / 不可证伪

> 判据：没有明确通过条件、或观测点未定义、无法用代码判定 PASS/FAIL 的表述。

### C1-1 · #3「重复解锁不重复扣费」的期望返回未定 — P0（阻塞判定）
- **位置**：`开发规划文档.md` M02 验收 #3；`系统-经营与成长.md` §5.1（"**幂等成功**（建议）返回 `changed=false`"）。
- **问题**："不重复扣费"只说了一半——**重复解锁该返回成功还是错误码，GDD 写的是"（建议）"**，不是已决。
- **为什么是问题**：验收 #3 无法判定 PASS/FAIL：若实现返回 `SLOT_ALREADY_UNLOCKED` 错误，算不算通过？若返回 `changed=false`，算不算？两种都"不重复扣费"，但契约不同，客户端（M06 解锁弹窗）行为也不同。
- **建议**：在 GDD §5.1 去掉"（建议）"，**拍板为幂等成功**：重复解锁同一 `slotId` 返回 `changed=false`、`coins`/`spent`/`unlockedSlots` 全部不变、**不写存档**。验收 #3 改为：「连续两次解锁同一 `slotId`，第二次返回 `changed=false` 且 `coins`、`spent`、`unlockedSlots`、`revision` 与第一次完全相同，存档文件字节不变」。

### C1-2 · #6「满铺加成生效/不生效」缺观测点、且"同层全部"范围含糊 — P0（阻塞判定）
- **位置**：`开发规划文档.md` M02 验收 #6（修正后）；`系统-经营与成长.md` §2.5、§4.2、§5.4、§6.1。
- **问题**：(a) "加成生效"在实现里是"该层 `unitPrice` 多了 +1"，但 `unitPrice` 在 §6.1 被标为「**建议派生返回**（可选）」——**如果 M02 不暴露 `unitPrice`，验收 #6 就没有稳定观测点**（只能从 `segments[].unitPrice` 反推）。(b) "同层全部处于「营业中」"未限定范围：应指「**该层全部铺位（含未开放的）**」，否则可能被误读为"已解锁的铺位全部营业中"——二层若只解锁 2/3 且都开业，按 GDD §4.2 公式**不算满铺**，但按含糊读法会算满铺。
- **为什么是问题**：观测点不定 → 无法用代码判定；范围含糊 → 同一个状态能读出两种结论（这正是"口径"类事故的温床）。
- **建议**：#6 改写为可判定版本——
  > 「给定某层，当且仅当该层**全部铺位（含未开放铺位）**都已解锁且 `prepared` 时，该层店铺的单客收益 = 等级单价 + `fullFloorBonus`；否则 = 等级单价。」
  并规定观测点：**至少 `segments[].unitPrice` 必须反映该值**（快照 `shops[].unitPrice` 建议一并返回，供 M06 展示"构成"）。

### C1-3 · #4「新等级单价」未界定是否含满铺加成 — P1
- **位置**：`开发规划文档.md` M02 验收 #4；`系统-经营与成长.md` §2.4、§4.2。
- **问题**："升级后新产生的收益按**新等级单价**记账"——这里说的是"等级单价"还是"单客收益 `unitPrice`（等级单价 + 满铺加成）"？
- **为什么是问题**：若某层已满铺，升级后应记账为"新等级 + 1"；若按字面"等级单价"实现会漏掉满铺项，段值算错。
- **建议**：#4 用词统一为 **`unitPrice`**（= 等级单价 + 满铺加成），并补一条用例：**满铺层内升级**，新段 `unitPrice` = 新等级单价 + 1。

### C1-4 · #5 在「已开业店铺数 = 0/1」时无通过条件 — P0（与 §3 C3-3 同源）

## 3. 缺失的边界（本任务重点）

> 只列 §5 边缘情况**未覆盖**的缺口；已覆盖且无问题的（如"金币不足零变化""重复开店幂等""时钟回退"）不复述。

### C3-1 · M01 的「金币下界」不变量在 v2 会误杀合法存档 — **P0（最严重）**
- **位置**：`internal/game/service.go` `validateState`（`state.Coins < s.cfg.InitialCoins` → "state counters out of range"）；对应 `系统-经营与成长.md` §5.5、§4.4。
- **问题**：M01 里金币只增不减，所以"`coins ≥ initialCoins`"是安全不变量。**v2 引入消费后，一次解锁/升级就会把 `coins` 降到 `initialCoins` 以下**——这条旧校验会**直接拒绝加载玩家自己的合法存档**。
- **为什么是问题**：这是"v2 变更让既有校验反向失效"的典型：不是缺功能，而是**既有保护会变成自锁**。触发路径极短（开局解锁一个 600 币铺位即触发），且表现是"存档损坏"，排查成本高。
- **建议**：§5.5 的"存档校验类"补一行：**金币下界由 `initialCoins` 改为 `0`**（`0 ≤ coins ≤ maxSafeInteger`）；并在验收中补用例：**解锁/升级扣费后重启进程，存档必须能正常加载自证**。

### C3-2 · 并发解锁 / 升级未进入 M02 验收 — **P0**
- **位置**：`开发规划文档.md` M02 交付物（单测清单）与 8 条验收；`系统-经营与成长.md` §5.2；对照 M07 验收 #2（"同一账号并发请求不会重复结算或重复扣费"）。
- **问题**：M02 新增**解锁**与**升级**两类写操作，但 **M02 的验收标准与单测清单都没有并发项**；GDD §5.2 只有"并发升级同一店 → M01 已实现并发保护"一句断言，**未证明 M01 的锁语义覆盖了解锁**。
- **为什么是问题**：M07 验收 #2 明确要求"不重复扣费"，而"不重复扣费"的**实现层保证在 M02**。若 M02 不落并发保护与测试，M07 会踩空——**这正是"带病开工"的同型风险**（把一条无法兑现的标准留给下游）。
- **核查结论（读代码）**：M01 的 `Service.mu` 串行化 `Prepare`/`Settle`，且 `mutate` 全程持锁、"先落盘再发布"。**只要解锁/升级也走同一把锁、在同一临界区内完成"校验金币 → 扣减 → 累加 `spent` → append 分段 → 落盘"，M01 的模型就足够**；但它**需要被显式扩展到新写操作并测试**，不能默认继承。
- **建议**：M02 验收补一条并发标准：
  > 「并发（≥100 次）解锁同一 `slotId`，只有 1 次 `changed=true`、`coins` 只扣一次、`spent` 只加一次、只多写 1 次存档；并发升级同一店同理；并发『解锁 + 结算』不得出现部分提交。」
  并明确：**解锁/升级与 `Prepare`/`Settle` 共用同一互斥锁与 `mutate` 提交路径**（金币检查与扣减在同一临界区，杜绝 TOCTOU）。

### C3-3 · 新档首日 / `openShopCount = 0` 的客流上限未定义 — **P0**
- **位置**：`系统-经营与成长.md` §2.3.2、§4.1、§3.5；`开发规划文档.md` M02 验收 #5。
- **问题**：`cap = baseVisitors + visitorsPerShop × openShopCount`，而新档开局两店均为「待开业」。§3.5 的档位表从"2 店 = 50"起，**没有 0 店 / 1 店档**。首次结算若发生在开店前，`cap = 20`；若在开店后，`cap = 50`。**同一新档，因客户端结算时机不同得到不同上限。**
- **为什么是问题**：验收 #5 与 D-01 不可判定；更严重的是**客户端（M05 每 5 秒轮询结算）会在玩家开店前先触发结算**，把首日上限冻结成 20，玩家无感受损——违反 P1/P3 的"慢慢变好"体感。
- **建议**：显式定义其一并写进 GDD/验收：
  - 方案甲（推荐）：**`dailyVisitorCap` 在业务日首次结算时按"当时的已开业数"冻结**，并**承认 0/1 店档**（20/35）合法；§3.5 表补 0 店 = 20、1 店 = 35 两行；补用例覆盖"首日先结算后开店 → cap=20，次日按新开业数重算"。
  - 方案乙：**cap 不在"首次结算"冻结，而在"业务日切换"冻结**（用日界瞬间的已开业数），当日开店次日生效的语义不变，但避免"结算时机决定上限"。二选一，**不可留空**。

### C3-4 · 分段账目：空分段（`visitors == 0`）是否允许未定义 — **P0**
- **位置**：`系统-经营与成长.md` §4.3、§5.4；`开发规划文档.md` M02 验收 #4。
- **问题**：§4.3 说"每次单价变化时 append 一条新分段"，但**没规定当该段内一个客人都没接待时怎么办**。触发场景真实存在：满铺层内升级后、或"某层补齐→满铺"后，若在下一次单价变化前无客人结算，就会出现 `{unitPrice, 0, 0}` 的空段。
- **为什么是问题**：验收 #4「**每一段** `revenue == visitors × unitPrice` 成立」的判定边界取决于此——空段算不算"一段"？若不允许空段，则必须有"懒创建/合并"规则；若允许，则校验必须接受 `0 == 0 × price`，且要说明空段是否计入 M06 店铺详情展示。**规则不定，则 #4 的边界不可判定。**
- **建议**：二选一并写进 GDD：
  - 甲（推荐，简单）：**允许空段**，校验接受 `revenue == visitors × unitPrice`（含 `0==0`），并声明"空段仅由单价变化产生、数量有界"；补用例。
  - 乙：**懒创建**——首次结算到该店才建段；则需定义"段尚未建立时 `unitPrice` 从何处取"，复杂度更高，不推荐。

### C3-5 · 一次 `prepare` 补齐整层时的分段顺序与范围未定义 — P1
- **位置**：`系统-经营与成长.md` §5.4（"满铺状态发生变化…该层所有店单价变化 → 各 append 一条新分段"）。
- **问题**：某店 `prepare` 使其所在层**恰好补满**时，需要**先置 `prepared=true`、再重算满铺、再为该层所有店 append 新段**。§5.4 只写了结果，没定义与 `prepare` 的先后、也没说**刚开业的这家是否也算"该层所有店"**。
- **为什么是问题**：顺序写反，刚开业的店自己会漏掉 +1（或旧价残留），与 #6 的正例直接冲突。
- **建议**：补一句硬顺序——「`prepare` 置位后立即重算该层满铺；若变为满铺，则为**该层全部店铺（含刚开业这家）**各 append 一条新分段，`unitPrice = 等级单价 + fullFloorBonus`」；补用例：一层两家依次开业，第二家开业后**两家**都产生 +1 新段。

### C3-6 · 「满铺 → 不满铺」未声明为不可能 — P1（团队已识别的高风险区）
- **位置**：`系统-经营与成长.md` §5.4（只写了"不满 → 满"一个方向）、§2.1 单调性约束。
- **核查结论**：**不可能。** 满铺 = 「该层全部铺位已解锁 ∧ 全部 `prepared`」。`unlockedSlots` 只增不减、`prepared` 只 `false→true`（关店已移除），两谓词均单调 ⇒ **满铺状态一旦成立就恒成立**，不存在反转。层内铺位集合固定（不会跨层移动），无中间态能破坏它。
- **为什么是问题**：**"不可能"也必须显式写出来**——否则读者无法区分"设计没考虑"与"设计证明不可能"，后续任何新增操作（如未来恢复关店/重排布局）都会静默破坏该前提。
- **建议**：§5.4 补一行「**满铺不可逆**：一旦某层满铺，该层此后恒为满铺（由 `unlockedSlots`/`prepared` 单调性保证）；不存在"满 → 不满"转移」；并建议 `validateState` 加一条不变量：**若某层已满铺，则该层铺位不得出现未解锁/未 `prepared`**（防手改档）。

### C3-7 · 同一店一日内多次单价变化的段数上界与用例缺失 — P1
- **位置**：`系统-经营与成长.md` §4.3（"单价变化仅两个触发点…每店分段数有界"）。
- **问题**：只有"有界"的定性结论，**没给上界与构造用例**。真实存在同日多次变化：一层咖啡 `待开业 →(prepare) 营业中(未满) →(花束 prepare) 满铺`，一天内两次单价变化。
- **为什么是问题**：验收 #4 需要"多次变化后逐段仍成立"的用例；上界是存档体积与校验成本的依据。
- **建议**：明确上界 **≤ 1(初始) + 4(升级) + 1(满铺) = 6 段/店**，并补用例：**同一业务日内先 `prepare` 补齐整层、再升级**，断言产生**两段新分段**且各段自洽、历史段不被改写。

### C3-8 · `spent` 的初始化与"旧档"处理 — P1（结论：非阻塞，但须显式声明）
- **位置**：`系统-经营与成长.md` §4.4、§5.5、§3.1；`adr/0004`；`开发规划文档.md` M02 风险行。
- **判断（回应团队提问）**：**不存在"历史档 `spent` 初值"问题**——M02 同时改动 **config**（删 `dailyVisitors`、加 `baseVisitors`/`visitorsPerShop`/`slots`/`fullFloorBonus`/`upgradeCosts`、改 `shops` 顺序）与 **schema**。按 ADR 0004，**config 一变指纹即变，全部 M01 存档被拒绝加载**，因此**没有任何 M01 存档会进入 v2**；v2 新档 `spent` 从 **0** 起。`spent` 是 schema 变更，但被"config 变更 ⇒ 指纹拒绝"**掩盖**，无需迁移。
- **为什么仍要写出来**：这条"被掩盖"的事实必须显式声明，否则将来**若有人只改 schema 不改 config**（或误以为拒绝来自 schema），就会得到"旧档带着 `spent=0` 被静默接受"的行为——虽然对 M01（无消费）恰好 `spent=0` 正确，但机制上不再受控。
- **建议**：M02 风险行与 §5.5 补明「v2 拒绝**全部** v1 存档，条件是 **`SchemaVersion` 与 `RulesFingerprint` 双重不符**」；`spent` 补边界校验（`0 ≤ spent ≤ maxSafeInteger`），并声明**扣币与 `spent` 累加在同一临界区原子完成**（防止"扣了币没记 spent"导致恒等式自证失败）。

### C3-9 · 业务日切换的原子性 + 日界处 `prepare` 与"冻结 cap"的次序 — P1
- **位置**：`系统-经营与成长.md` §2.3.2、§5.3；M01 `accrue` 的日刷新。
- **核查结论**：跨 0 点**并发**结算由 M01 互斥锁串行化，**原子性本身有保证**（每个请求各自看到一致的 `BusinessDay`）。
- **缺口**：跨日**重算 cap 用的 `openShopCount`** 与"日界处 `prepare`"的**先后**会改变当日 cap——在日界与首次结算之间 `prepare` 的店计入 cap，之后不计。这与 C3-3 的"冻结时机"是同一问题的两面。
- **建议**：随 C3-3 一并定义；补用例：**23:59 结算 → 跨 0 点后立即 `prepare` → 再结算**，断言 cap 与 `VisitorsRemaining` 的期望值（明确 `prepare` 是否计入当日）。

### C3-10 · `unlockedSlots` 的序列化 / 顺序 / 去重 / 加载校验未定义 — P1
- **位置**：`系统-经营与成长.md` §3.1（只列字段名）、§3.2；M01 `State`（无该字段）。
- **问题**：State 里 `unlockedSlots` 的 JSON 形状（数组？顺序？）、是否允许重复、加载时是否拒绝"重复 / 未知 slotId / 未按 `unlockOrder` 顺序解锁"的档，均未定义。
- **为什么是问题**：`validateState` 需据此判定，否则手改档可绕过解锁顺序（验收 #2/#7 的守门就漏了）。
- **建议**：定义 `unlockedSlots` 为**按 `unlockOrder` 升序的 `slotId` 数组、无重复、必为配置内已知铺位**；`validateState` 拒绝：重复项、未知 `slotId`、**跳序解锁**（存在 `unlockOrder=n` 却缺 `n-1`）、以及"已解锁铺位数为 0/超配置"。补对应用例。

### C3-11 · 升级对象的状态限制未定义 — P1
- **位置**：`系统-经营与成长.md` §2.4、§5.2。
- **问题**：能否升级「待开业」（已解锁未开店）的店？升级「未开放」的店应返回什么？§5.2 只覆盖"已满级再升级""金币不足"。
- **为什么是问题**：直接影响验收 #4 的前置构造（升级前该店必须处于什么状态），也影响 M06 升级入口的禁用态。
- **建议**：明确——升级**未开放**铺位 → `SLOT_LOCKED`；升级**待开业**店 → **允许**（`level` 与 `prepared` 正交，升级不改开业状态），或明确禁止，二选一。补用例覆盖所选分支。

### C3-12 · 数值上限（`NUMERIC_LIMIT`）守卫未覆盖新字段 / 新写路径 — P2
- **位置**：`internal/game/service.go`（`maxSafeInteger` 守卫针对 `Coins`/`Revenue`/`Visitors`/`Revision`）；`系统-经营与成长.md` §5.5。
- **核查结论**：`spent` 实际有界（解锁 2600 + 升级 21000 ≈ **23600**），**不会**触及 `2^53-1`；`dailyVisitorCap` 亦小。但 M01 的守卫是**逐字段硬编码**的，**不会自动覆盖新字段/新路径**。
- **建议**：显式把守卫扩展到**解锁扣减、升级扣减、`spent` 累加、分段内 `visitors`/`revenue` 的乘除边界**（分段单价改为动态 `unitPrice`，M01 的 `maxSafeInteger/price` 需按段计算）；补用例"触及上限不写部分结果"（沿用 M01 口径）。

## 4. 数值口径

### C4-1 · 待确认项 7/8 **不会**让任何 M02 验收标准不可判定 — 结论（附约束）
- **位置**：`开发规划文档.md` §8 待确认项 7（"解锁 vs 升级取舍不成立"）、8（"满铺口径两套混用"）；`系统-经营与成长.md` §3.6、§4.5、§4.6、附录 A①②、附录 B。
- **判定**：逐条核对 M02 的 8 条验收标准——**没有一条含具体金额/阶段产出断言**：
  - #1/#2/#3 只涉及失败/幂等语义（与数值无关）；
  - #4 是**恒等式**（`revenue == visitors × unitPrice`），与口径无关；
  - #5 依赖**客流公式**（`base + per × count`，已拍板），与满铺口径无关；
  - #6 依赖**满铺规则**（固定 +1，已拍板），与"含/不含满铺"的**统计口径**无关；
  - #7/#8 与数值无关。
  因此**两项待确认项均不阻塞 M02 验收判定**。补充：GDD §8.2 的 **D-07（逐档日均增量为正）** 在"含满铺"与"不含满铺"两套口径下**结论都成立**（§3.6 已注明），故也不受影响。
- **必须附加的约束（否则会人为制造不可判定）**：
  1. **M02 的测试断言不得硬编码 `§3.6` 的阶段产出数字**（375 / 582 / 626 / 740 / 950 / 1672）——这些正是两套口径的争议点。应断言**公式**（`cap = base + per × openCount`）与**恒等式**，而非派生总数。
  2. **回本天数（§4.6）不得进入任何验收断言**——它是 G5 定稿的输入，不是 M02 的验收对象。
- **一句话**：待确认项 7/8 属 G5 数值定稿范围（用户已拍板留待 G5），**M02 可与其解耦**；只要遵守上述两条约束，口径问题不进入 M02 的质量门。

### 6.2 §3.5 推理与「未冻结」表示

- **「0 档不可达」推理成立**：冻结前提为 `openShopCount ≥ 1`，且「实际产生客人」蕴含至少一家营业中店铺 ⇒ 冻结值 ≥ `base + 1×per = 35 > 20`。0 档确非可达冻结值，不列正确。**1 店行 35 正确**（20+15），且因未满铺不含加成（35×6=210 校验无误）。
- **但「未冻结」状态用什么表示，GDD 未写**（§3.5/§5.3 只说「视为未冻结、不是 20」）→ **新缺口 N-1**。

### 6.3 新增缺口（复核发现）

- **N-1【新 P0 · C3-3 衍生】**「未冻结」表示未定义，连带三处未定：
  1. 存档 schema 里 `dailyVisitorCap` 的未冻结表示（`null`/指针？哨兵值？独立布尔标志？M01 的 `State` 用非指针 `int64`，零值 0 会与"未冻结"冲突，必须显式决定）。
  2. **冻结前 `VisitorsRemaining` 的初值**（M01 是 `= DailyVisitors`，v2 此时无 cap 可依）。
  3. **settle 的冻结算法顺序**：必须先「存在 ≥1 个间隔的待产生客人 ∧ `openShopCount ≥ 1`」→ 冻结 cap → 置 `VisitorsRemaining = cap` → 再服务；否则若 `VisitorsRemaining` 初值为 0，会形成「无客人 → 永不冻结」的死锁。
  **影响**：决定存档格式，并使验收 #5「0 店不冻结、不落盘」无从断言。**必须在 M02 落 schema 前补齐。**

### 7.3 C — SC-P2-005 新增三项（判定：✅ 达标）

**C-1 §4.3 三个分段触发点 + `prepare` 硬顺序 —— ✅ 自洽、无重复计入、结论成立。**
- 三个触发点：① 开店（`prepare`，建**首个分段**）② 升级 ③ 所在层满铺状态变化。
- 硬顺序「① 置 `prepared` → ② 重算满铺 → ③ 建/append 段（`unitPrice` 取重算满铺**之后**的值）」。
- **与 §5.4 是否重复计入**：§5.4 写「该层所有店单价变化 → 各 append 一条新分段」，其括注**显式排除**触发店（「触发满铺的新开业店建立其首个分段、直接为 bonus 价，不产生 pre-bonus 空段」）。§5.6 进一步区分「触发店 → 1 条 bonus 段」/「该层**其他已开业店** → 各 1 条新段」。**无重复计入。**
- **结论「触发店只产生一条 bonus 价段、无 spurious pre-bonus 空段」站得住**：因置位与重算满铺均在建段**之前**、且在同一原子操作内，该店从未以 pre-bonus 价存在过一个「分段区间」，不应留下 `visitors==0` 的 pre-bonus 段。**推理正确。**

**C-2 §3.7 `unlockedSlots` 规格 —— ✅ 可实现、与 §5.5 / §6.1 一致。**
- 序列化（有序 `string[]`，不用位掩码）/ 顺序（写入规范序、读取不因序拒绝）/ 去重（不允许重复）/ 加载校验（未知 `slotId`、跳序、重复、数量越界 ⇒ 存档损坏）四项齐备。
- **可实现性**：可落到 `validateState` 一类校验函数——成员检查（`slotId ∈ config.slots[].id`）、去重检查、`unlockOrder` **前缀**检查（`{全部 unlockOrder=0} ∪ {1..m}`，`m∈[0,3]`，注意 `unlockOrder=0` 有**两个**铺位）、数量 `[2,5]` 检查，均为线性可判定。与 §5.5 校验表、§6.1 客户端字段（`unlockedSlots[]` 按 `unlockOrder` 升序、无重复）一致。
- **★ 裁定（design-strategist 的取舍「写入强制规范顺序、读取不因顺序拒绝」）—— 取舍正确，应保留，不改「严格拒绝」。**
  理由：
  (a) **数组顺序不携带业务语义**——校验关心的三条（未知 / 跳序 / 重复）均与顺序无关；顺序只是「集合的序列化呈现」。
  (b) **严格拒绝会产生假阳性**：一个语义完全等价、仅元素顺序不同的存档会被误判为「损坏」而拒载——这与 M01 基线「拒绝**被改坏**的存档」的意图相反，且违反需求 4.7「不得静默清零」的**对称面**（不应把合法存档当损坏）。
  (c) **规范序写入 + 读取规范化**已同时满足「字节稳定」（写入侧确定）与「兼容性」（读取侧宽容），是最优解。
  **唯一附带约束（建议写入验收）**：不得断言「加载一份**非规范序**存档后字节不变」——若该存档后续触发写入，会被规范化（顺序改变、字节改变），这是**预期行为**，测试口径需与此一致。

**C-3 §5.4 满铺不可逆（C3-6）+ §4.3 段数上界 ≤6（C3-7）—— ✅ 上界推导正确。**
- **满铺不可逆**：满铺谓词 =「该层全部铺位已解锁 ∧ 全部 `prepared`」，两合取项均单调（`unlockedSlots` 只增、`prepared` 只 `false→true`）⇒ 一旦成立恒成立，层内铺位集合固定，无中间态可破坏。**正确。**
- **上界 `1（初始/开店）+ 4（升级）+ 1（满铺）= 6`**：升级 `Lv1→5` 恰 4 次、每次 append；满铺不可逆 ⇒ 至多一次。**作为上界成立**（注：**触发满铺的那家店**其「初始段」与「满铺段」是**同一条**（§4.3 只产生一条 bonus 段），实为 5 段；故 6 是**偏松但正确**的上界，非紧界——不影响存档体积/校验成本结论）。全局 `≤ 5 店 × 6 = 30` 段正确。

### 7.4 D — ADR 0003 的文档处理方式（判定：⚠️ 处理可接受，但需 codify）

### 8.3 复核发现（按严重度）

#### 🔴 P1-A 空闲结算落盘且 `changed=true`，与 GDD §5.7.2 明文相反（实测）

- **规格**：GDD §5.7.2「**0 店开业的结算**：`changed = false`，**不写** `capFrozen`、**不写** `dailyVisitorCap`」。
- **实现**：`mutate`（`service.go:421-450`）只在「`apply == nil` 且 `now` 与 `LastObservedAt` 全等」时短路；只要时间前进了 1 纳秒，就走 `Revision++` → `store.Save` → `Changed = true`。`accrue` 的 `openShops == 0` 分支（`service.go:470-473`）虽然正确地**不改** `capFrozen`/`dailyVisitorCap`，但仍把 `LastAccrualAt` 推到 `now`，于是每次轮询都算「有变化」。
- **实测**（探针 `P-A`）：零开业连续 3 次 settle → `changed=true / revision=2,3,4 / 落盘次数=2,3,4`。
- **实测**（e2e，真实 HTTP）：`prepare coffee` 后两次「间隔未满」settle → `rev 3 → 4`、`changed=true`、`earned=0 used=0`；已冻结后再 settle → `rev=6 changed=true earned=0`。
- **三处一致地声称「不落盘」**：GDD §5.7.2、`docs/M02-后端扩展.md` §7.2 #5（「0 店开业不冻结、**不落盘**」）、以及单测 `service_test.go:1237` 的注释「0 店开业：反复结算都不冻结、**不落盘**」——**但该注释下一行断言的是 `changed=true`**。测试把与规格相反的行为固化成了期望，属**写验同源**，这正是本轮必须独立复跑的理由。
- **影响**：① M04/M05 客户端每 5 s 轮询在空闲期会收到 `changed=true` 但数值全等的响应，若按 `changed` 决定是否刷新/播动画即做无谓功；② `revision` 无实质含义地单调膨胀（每天约 1.7 万次）；③ M07 存档上云后，空闲期变成**每 5 s 一次云端写请求**。
- **不影响**：任何玩法正确性与存档自证（落盘值仍满足 §5.7.3 二态校验，`capFrozen=false` 时 `dailyVisitorCap` 恒为占位 `0`）。
- **处置二选一，需裁定**：
  - **A 改实现**（推荐，约 5 行）：`mutate` 增加「除 `LastObservedAt`/`LastAccrualAt` 外是否有实质变化」判定，无变化则 `changed=false` 且不落盘；同步把 `service_test.go:1237` 起的断言改为 `changed=false`。
  - **B 改规格**：删去 §5.7.2 的 `changed = false` 承诺（保留「不写 cap 两字段」），并同步 `开发规划文档` M02 验收 #5 与实现文档 §7.2 #5 的表述。

#### 🟠 P1-B `Config.Validate()` 未禁止两个铺位共用同一 `(floor, position)`，导致 shop↔slot 映射塌陷（实测）

- **实测**（探针 `P-F`）：把 `f2-s3` 改为与 `f2-s2` 同 `(floor, position)` 且同 `shopId` → **`Validate()` 返回 nil**，`NewService` 正常构建，无告警。
- **根因链**：`validateSlots`（`config.go:132-171`）只校验 slot **ID** 唯一 + `floors[1]==2 && floors[2]==3` 的计数，既未校验 `(floor,position)` 唯一，也未校验「每个 shop 被恰好一个 slot 覆盖」（双射只做了单侧）。位置重复时 `slotIDOfShop`（`service.go:200-207`）对未覆盖的店返回 `""`，而 `s.slotIndex[""]` 是 map 缺失键 → **静默取 0**，于是 `shopSlot` 让该店指向 `cfg.Slots[0]`（`f1-s1`）的铺位。
- **后果**：该店的「铺位是否解锁」「本层是否满铺」判定读到**错误铺位**。实测中 `bookstore` 的 `unitPrice` 变 10、升级返回 `SHOP_NOT_OPEN`（掩盖了它本应因未解锁而返回 `SLOT_LOCKED`）。不 panic、不毁档，但门禁判定错位且**零报错**。
- **为何当前不触发**：`config/development.json` 的 5 条 slot 位置互不重复。**但** ADR 0004 把 config 定义为「人手改数值」的唯一场所，改数值时复制粘贴一行 slot 即中招，且校验不会拦。
- **处置**（建议顺手修，约 6 行、零行为变更风险）：`validateSlots` 补 ① `(floor,position)` 集合大小 == `len(Slots)`；② 每个 shop 的 `(floor,slot)` 必须出现在该集合中（双射）。另可让 `slotIDOfShop` 返回 `(string, bool)` 并在 `buildLayout` 显式报错，消除静默取 0。

#### 🟡 P2-A §5.5「轮询游标指向已开业店铺」未实现，且**按字面实现会误拒合法存档**

- **实测**（探针 `P-E`）：`prepare coffee` + 一次产生客人的 settle 后，已提交存档的 `nextShopIndex=1` 指向 `flowers`（`prepared=false`），`validateState` 通过、加载正常。
- **根因**：游标推进是 `state.NextShopIndex = (index+1) % len(state.Shops)`（`service.go:514`），**落在未开业店上是正常运行的常态**，跳过动作发生在下次 `accrue` 的 while 循环（`service.go:490-492`）。
- **结论**：这不是实现漏写，而是 §5.5 那行「校验规则」的表述与 §4 的游标语义冲突——照字面加校验会把合法档判为损坏。建议把 §5.5 该行改写为「**结算时游标须跳过未开业店铺；落盘值本身不作校验**」，并在 ADR 0002 加一句注解。不阻塞。

#### 🟡 P2-B §5.6「每店分段数 ≤ 6」未落为加载校验

- **实测**（探针 `P-D`）：把 `clothing` 的分段替换为 **20 段全空段**（逐段恒等式、聚合值、金币恒等式全部仍成立）→ `validateState` **接受**。
- **同时实测上界成立且是紧的**：走「先开业（无加成）→ 他店补齐本层触发满铺 → 升满 4 级」的最长路径，`clothing` 恰得 **6 段 `[12,13,15,17,20,23]`**，e2e 的 `coffee` 亦为 6 段 `[6,7,8,9,11,12]` → §5.6 的 `1+4+1` 推导正确。
- **判定**：实现侧 ≤6 由逻辑保证（`floorFull` 只可能 false→true 一次、等级单价只增、`syncSegments` 同价不 append），故非缺陷；「越界即毁档」在本模块不可达。**风险只在 M07**——一旦服务端开始接收外部提交的存档，该上界需成为校验项。建议登记为 M07 前置，不改 M02。
