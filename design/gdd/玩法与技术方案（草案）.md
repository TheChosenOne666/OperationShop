# A 玩法方案

## A1 核心循环

```
打开游戏
  → 一眼看到今天的客流与金币
  → 做一件花钱或赚钱的事（开店 / 解锁铺位 / 升级店铺）
  → 客人按固定节奏到店，金币缓慢增长
  → 当天客流耗尽，收益停在当天的上限
  → 次日 0 点客流恢复，回到第一步
```

循环的**长度是"一天"**：玩家不需要在一天内多次回来，也没有任何"错过就亏"的时间窗。

## A2 楼层与铺位

| 层 | 铺位 ID | 位置 | 对应店铺 | 解锁条件 |
| --- | --- | --- | --- | --- |
| 二层 | `f2-s1` | 左 | 衣橱 | 600 金币 |
| 二层 | `f2-s2` | 中 | 甜屋 | 800 金币 |
| 二层 | `f2-s3` | 右 | 书店 | 1200 金币 |
| 一层 | `f1-s1` | 左 | 咖啡 | 开局已解锁 |
| 一层 | `f1-s2` | 右 | 花束 | 开局已解锁 |

- 二层必须**从左到右依次解锁**（不能跳过中间直接开右边）。
- 铺位与店铺在 v1 是**一对一固定绑定**。v1 不做店铺换位（换位会牵动存档模型与美术表现，列入后续版本）。
- 未解锁的铺位显示为空铺（绿棚木门、橱窗为空）。

## A3 单客收益

```
单客收益 = 该店当前等级的单价 + 该层满铺加成(0 或 1)
```

**等级单价表（初版）**

| 店铺 | Lv1 | Lv2 | Lv3 | Lv4 | Lv5 |
| --- | --- | --- | --- | --- | --- |
| 咖啡（一层） | 6 | 7 | 8 | 10 | 11 |
| 花束（一层） | 9 | 10 | 12 | 14 | 16 |
| 衣橱（二层） | 12 | 14 | 16 | 19 | 22 |
| 甜屋（二层） | 8 | 9 | 11 | 13 | 15 |
| 书店（二层） | 10 | 12 | 14 | 16 | 19 |

**满铺加成（v1 唯一的"搭配"规则）**

- 该层所有铺位**都已解锁且都已开业** → 该层每家店的单客收益 **+1 金币**。
- 一层满铺（2/2）与二层满铺（3/3）各算各的，互不影响。
- 关掉任意一家店，该层加成立即消失。

> 为什么用"固定 +1"而不是"百分比 +10%"：百分比会让 6 变 6.6、9 变 9.9，产生小数和四舍五入误差，低等级升级会被取整吃掉。固定加值全程整数，玩家看得懂，服务端也好校验。

## A4 客流模型

- **到店间隔**：初版 5 秒一位。
- **每日客流上限**：`基础 20 + 每家已开业店铺 × 15`

| 已开业店铺 | 客流上限 |
| --- | --- |
| 咖啡 + 花束 | 50 |
| + 衣橱 | 65 |
| + 甜屋 | 80 |
| + 书店 | 95 |

- 上限在**每天业务日第一次结算时确定并写死当日值**。当天中途开店不补当天客流，次日生效。
- 客人按固定顺序轮转并**跳过未开业的店铺**：
  `咖啡 → 花束 → 衣橱 → 甜屋 → 书店`
- 不足一个到店间隔的时间余量**结转到下一次结算**，不丢弃。
- 跨业务日只刷新当天客流，**不补算离线期间的历史客流**，也不扣除任何东西。

### 为什么客流上限要跟着店铺数量涨

如果客流上限固定，开一家单价低于当前均价的店会**把同一批客人分走，导致日均收益下降**。用固定上限 50 算一遍就能看到这个反向激励：

| 已开业店铺 | 轮转顺序 | 日均收益（固定 50 客流） | 变化 |
| --- | --- | --- | --- |
| 咖啡 + 花束 | 6, 9 | 375 | — |
| + 衣橱 | 6, 9, 12 | 447 | +72 |
| + 甜屋 | 6, 9, 12, 8 | **435** | **−12（花了 800 金币反而变差）** |
| + 书店 | 6, 9, 12, 8, 10 | 450 | +15 |

改成"客流随店铺增长"后，每一家新店都有明确回报，解锁成本才有意义：

| 已开业店铺 | 客流上限 | 日均收益（全 Lv1） | 较上一档增量 |
| --- | --- | --- | --- |
| 咖啡 + 花束 | 50 | 375 | — |
| + 衣橱 | 65 | 582 | +207 |
| + 甜屋 | 80 | 700 | +118 |
| + 书店 | 95 | 855 | +155 |

## A5 经济模型

### 产出

`当日产出 = 客流上限内轮转到的每一位客人的单客收益之和`

各阶段日均产出（含满铺加成）：

| 阶段 | 日均产出 |
| --- | --- |
| 开局（一层 2 店 Lv1） | 375 |
| 二层全部解锁（5 店 Lv1，满铺加成生效） | 950 |
| 五店全部满级（Lv5 + 满铺） | 1672 |

### 消耗

| 项目 | 单价 | 说明 |
| --- | --- | --- |
| 解锁 `f2-s1` 衣橱 | 600 | 日均 +207 → 约 3 天回本 |
| 解锁 `f2-s2` 甜屋 | 800 | 日均 +118 → 约 7 天回本 |
| 解锁 `f2-s3` 书店 | 1200 | 日均 +155 → 约 8 天回本 |
| 店铺升级 Lv1→2 | 300 / 店 | 五店共 1500 |
| 店铺升级 Lv2→3 | 700 / 店 | 五店共 3500 |
| 店铺升级 Lv3→4 | 1200 / 店 | 五店共 6000 |
| 店铺升级 Lv4→5 | 2000 / 店 | 五店共 10000 |

- 解锁全部二层铺位的总投入 **2600 金币**，按开局 375/天计算约需 7 天（期间还会同步升级一层）。
- 五店全部满级的总投入 **21000 金币**，属于长线目标（从 950/天 提到 1672/天，回收期约 29 天）。**不要求玩家达成**。
- 金币只进不出的情况在设计上被排除了：只要有没解锁的铺位或没满级的店，金币就一直有去处。

### 失败态

**没有。** 没有破产、没有倒闭、没有客流差评、没有负债。玩家唯一的"惩罚"是进度慢一点。

## A6 业务日与离线

- 业务日按 `Asia/Shanghai` 的 0 点切分（与 M01 已实现的规则一致）。
- 跨业务日：刷新客流上限与剩余客流，**累计收益与店铺状态全部保留**。
- 离线：不产生收益，也不扣任何东西；不弹"你离开了 3 天"。
- 服务器时钟回退时拒绝结算（避免重复计算），M01 已实现。

## A7 好友经营排行榜

- 排序依据：**总金币**（服务端权威值）。
- 数据来源：客户端把服务端返回的金币上报到微信托管数据，再用开放数据域读取好友数据并渲染排行榜。
- 一个好友都没有时：显示自己的分数与名次，不留空白页。
- 第一版不做互访、互助、留言。设计图里的邮戳信纸（`13.jpg`）留给后续的互访留言功能。

# B 技术方案

## B1 术语对照（写给不熟悉游戏引擎的人）

读下面的方案前先对一下词。引擎里的概念基本都能映射到通用前端/后端概念：

| Cocos / 引擎概念 | 等价于你熟悉的东西 | 在本游戏里指什么 |
| --- | --- | --- |
| 场景 Scene | 一个页面 / 一个路由视图 | `Boot` 启动场景、`Mall` 主界面场景 |
| 节点 Node | DOM 元素 | 楼层、铺位、按钮、文字都是节点，靠父子层级组织 |
| 组件 Component | 挂在元素上的行为脚本（类似 React 组件 / 混入） | `ShopView` 负责一家店的状态与显示 |
| 预制体 Prefab | 可复用的组件模板（一次定义、多处实例化） | `Guest` 预制体，每来一位客人实例化一个 |
| 资源 Asset / Bundle | 静态资源 / 代码分割后的懒加载 chunk | 店铺立绘放独立 Bundle，不进首包 |
| 帧循环 `update(dt)` | `requestAnimationFrame` 回调 | 推进客人走动的每一帧 |
| 锚点 Anchor / 坐标系 | CSS 的定位原点 + `transform-origin` | 铺位对齐靠锚点，不靠手调像素 |
| 图集 Atlas（自动图集） | 雪碧图 sprite sheet | 把 UI 小图合并，减少渲染批次 |
| Draw Call | 一次 GPU 绘制批次 | 太多会掉帧，所以要合图集 |
| 补间 Tween | CSS `transition` / `animation` 的代码版 | 金币飘字、客人走位 |

## B2 总体架构与职责划分

```
微信小游戏客户端（Cocos Creator 3.8.8，工程 NewProject/）
        │  HTTPS + 会话令牌
        ▼
Go 服务端（模块 streetcorner，仓库根目录）
        │
        ▼
存档（开发期：本地单文件 / 上线后：云端存储）
```

**职责红线**

| 归服务端 | 归客户端 |
| --- | --- |
| 金币、客流、收益、等级、解锁状态 | 展示与动画 |
| 业务日判断与跨日刷新 | 玩家操作意图的收集与提交 |
| 时间推进与时间余量 | 请求节流、重试、错误提示 |
| 所有数值计算 | 不做任何数值计算，也不上报金币/时间/客流 |

M01 已经把这条红线用接口约束住了：`POST` 命令只接受空 JSON 对象 `{}`，客户端塞任何字段都会被 400 拒绝（已实现并有测试覆盖）。

## B3 客户端方案

### B3.1 引擎与目标平台

- 引擎：Cocos Creator **3.8.8**（`NewProject/package.json` 已确认）。
- 构建目标：**微信小游戏**。目前工程是全新未配置状态（无设计分辨率、无资源、无 AppID）。
- 构建产物需要在微信开发者工具里跑通，才能进入实机验证。

### B3.2 分辨率与适配

- 设计图 `主界面图.jpg` 为 1080×1918，比例 9:16。
- 设计基准分辨率取 **750×1334**（同为 9:16，便于按 1.44 倍关系换算设计图的像素值）。
- 适配策略：**等比缩放 + 高度贴合（Fit Height）**，宽度方向按机型实际比例左右延展，超出 9:16 的机型用背景延伸而不是拉伸主体。
- 底部 HUD 固定在屏幕底部，并避开 iOS 底部横条安全区。

### B3.3 场景与节点结构

```
Boot（启动场景）
  └─ 拉取 /api/v1/config 与 /api/v1/mall → 进入 Mall
Mall（主界面场景）
  ├─ Marquee        顶部招牌「街角商场」+ 绿色雨棚
  ├─ Floor2         二层楼面
  │   ├─ Railing    木栏杆 + 猫（装饰）
  │   └─ Slot ×3    f2-s1 / f2-s2 / f2-s3
  ├─ Floor1         一层临街
  │   ├─ Staircase  中间楼梯（装饰）
  │   └─ Slot ×2    f1-s1 / f1-s2
  ├─ GuestLayer     客人层（运行时动态实例化）
  └─ Hud            底部 HUD（固定）
      ├─ CoinIcon + CoinLabel
      ├─ NavButton ×3（经营 / 布局 / 好友）
      └─ VisitorLabel（已到店 / 上限）
```

**关键预制体**

| 预制体 | 说明 |
| --- | --- |
| `Slot` | 一个铺位。三种表现：未解锁（空铺立绘）、已解锁未开业（空铺 + 开门状态）、已开业（对应店铺立绘） |
| `ShopView` | 店铺立绘 + 招牌，挂在 `Slot` 下 |
| `Guest` | 一位客人。正/侧/背三视图按行走方向切换 |
| `Hud` | 底部木条底板 + 金币 + 三个圆形按钮 + 客流 |
| `Panel` | 通用圆角木面板（`10.jpg`），所有弹窗复用 |

### B3.4 资源管线

1. **素材必须先抠图**：现有 19 张图全是 JPG，`3/4/5/7/8/9` 等看起来透明其实是烘焙进图里的棋盘格，JPG 本身也没有 alpha 通道。**全部素材需要统一跑抠图流水线转成真正的透明 PNG**，再压缩后导入。
2. **目录约定**
   ```
   assets/scenes/        Boot / Mall
   assets/prefabs/       Slot / ShopView / Guest / Hud / Panel
   assets/textures/shop/ 店铺立绘、空铺位底图
   assets/textures/ui/   HUD 底板、图标、面板
   assets/textures/guest/ 客人
   assets/scripts/       组件脚本
   ```
3. **首包/分包策略**：启动必需的 UI 底图与图标进主包；店铺立绘、空铺位底图放独立 Bundle（等价于前端懒加载 chunk），按需加载。主包体积上限需按官方最新文档核对。
4. **合图集**：UI 小图（图标、按钮）走自动图集合并，减少 Draw Call。

### B3.5 表现层（v1 最小可玩）

- 客人：从商场入口沿路径走到目标店铺门口 → 停留约 0.5 秒 → 店铺位置金币飘字 → 淡出消失。
- 客人外观按行走方向切三视图（`6.jpg` 已提供正/侧/背）。
- 店铺状态区别：已开业用原立绘，未解锁用空铺位底图（`1.jpg` / `2.jpg`）。
- 金币变化用 Tween 补间数字滚动，不做逐枚硬币飞行动画（省性能）。

### B3.6 与服务端的同步节奏

- 进入前台 / 打开游戏：拉一次 `/api/v1/mall` 全量快照。
- 停留在主界面期间：每 5 秒调一次 `POST /api/v1/mall/settle` 拉增量，返回体自带最新快照与本次收益，客户端只做补间动画。
- 切到后台：停止轮询，回到前台立即拉一次快照（服务端会把这段时间的客流算出来）。
- **客户端不跑"虚拟时间"**：界面上的客流与金币永远以最近一次服务端响应为准。

### B4.1 M01 已实现

### B4.2 需要新增

| 方法 | 路径 | 入参 | 说明 | 所属模块 |
| --- | --- | --- | --- | --- |
| POST | `/api/v1/slots/{slotId}/unlock` | `{}` | 解锁铺位，`slotId` 形如 `f2-s1` | M02 |

**错误码沿用 M01 已定义的稳定集合**（`INVALID_COMMAND` / `UNAUTHORIZED` / `LOCAL_ONLY` / `ORIGIN_DENIED` / `SHOP_NOT_FOUND` / `CLOCK_BACKWARDS` / `NUMERIC_LIMIT` / `BODY_TOO_LARGE` / `JSON_REQUIRED` / `SAVE_FAILED`），新增：

| HTTP | code | 触发条件 |
| --- | --- | --- |
| 409 | `SLOT_LOCKED` | 目标铺位尚未解锁 |
| 409 | `SLOT_ORDER` | 试图跳过顺序解锁二层铺位 |
| 409 | `INSUFFICIENT_COINS` | 金币不足 |
| 409 | `ALREADY_UNLOCKED` | 重复解锁（幂等返回成功也可，需二者择一，建议幂等成功） |
| 409 | `MAX_LEVEL` | 已满级仍请求升级 |

### B4.3 好友排行榜

排行榜**不需要新增服务端接口**：

1. 客户端从 `/api/v1/mall` 拿到服务端权威金币；
2. 主域调用微信托管数据接口上报自己的金币；
3. 开放数据域读取好友数据，在子域内渲染排行榜。

> 注意：开放数据域是独立沙箱，不能访问主域的资源与节点；好友相关能力需要用户授权，**具体授权入口与限制必须在动手前核对官方最新文档**，不要凭记忆实现。

## B5 服务端需要的变更

M01 已具备：规则配置校验、开店、结算、客流轮询、业务日刷新、时间余量结转、原子存档、仅本机访问、令牌认证、幂等与并发保护。

需要扩展的部分：

### B5.1 规则配置（v1 → v2）

- 新增每铺位解锁价格、解锁顺序。
- 新增店铺等级单价表（5 店 × 5 级，整数）。
- 新增满铺加成值（固定 +1）。
- 把 `dailyVisitors` 从固定值改为 `基础客流 + 单店客流`。
- 一句话：**调数值只改配置，不改代码**（M01 已支持这条）。

### B5.2 存档 schema（v1 → v2）

新增字段：

| 字段 | 说明 |
| --- | --- |
| `unlockedSlots[]` | 已解锁的铺位 ID |
| `dailyVisitorCap` | 当日客流上限。跨日刷新时确定后**写死当日值**，否则当天中途开店会改变当日上限 |
| `spent` | 累计支出（解锁 + 升级） |
| `shops[].level` | 店铺等级 1–5 |
| `shops[].segments[]` | 账单分段，见下 |

**账单分段（推荐方案 A）**

把每家店的累计收益改为分段记录：单价每变化一次就新开一段。单价变化只有两个触发点——升级、所在层满铺状态变化——所以每店最多几段，总量可控。

```
shops[i].segments = [ { unitPrice, visitors, revenue }, ... ]
```

校验时对每一段要求 `revenue == visitors × unitPrice`，仍然保持 M01 那种"存档可自证"的强校验。

- 方案 B（更省事）：不存分段，只校验金币恒等式 `coins == initialCoins + Σrevenue − spent`，不做逐笔可追溯。
- **推荐方案 A**：M01 已经把"存档能自证账目"当成设计基线，放弃它会让一份被改过的存档无法被发现，而分段方案的实现成本只是每次改价时 append 一条。

### B5.3 校验规则调整

| 规则 | M01 | v2 |
| --- | --- | --- |
| 金币恒等式 | `coins == initialCoins + Σrevenue` | `coins == initialCoins + Σrevenue − spent` |
| 每店账目 | `revenue == visitors × 固定单价` | 逐段 `revenue == visitors × unitPrice` |
| 未开业店铺 | 不得有累计客流 | **放宽**：关店后要保留累计，改为「**未解锁铺位不得有累计客流与收益**」 |
| 客流上限 | 固定配置值 | 与存档中的 `dailyVisitorCap` 一致，且不超过理论上限 |
| 轮询游标 | 指向已准备店铺 | 跳过未解锁与未开业的店铺 |

### B5.4 版本兼容

以上变更会改变规则指纹。按 M01 现有机制，**旧存档会被拒绝加载**——这是预期行为而不是 bug。上线前没有真实用户，开发期直接删除旧存档文件即可，不需要写迁移工具。

### B5.5 微信登录与云端存档（M07）

- `code2session` 换取 openid 与 session_key，签发会话令牌替代当前的本地开发令牌。
- M01 的本地开发令牌与仅本机访问限制**必须在上线前彻底关掉**，不能带到线上。
- 会话令牌要有过期时间；同一账号的写操作由 M01 已有的互斥锁串行化。

### B5.6 日志与可观测

- 结算、解锁、升级、关店四类写操作都要有可追踪日志（方法、路径、耗时、结果码）。
- 日志**不记录令牌、查询参数与个人信息**（M01 已实现并有测试覆盖）。

## B6 存档与容错

| 场景 | 处理 |
| --- | --- |
| 写入过程中断电 | 先写临时文件、`fsync` 后原子替换，不会出现半个存档（M01 已实现） |
| 存档损坏 | 拒绝启动并保留原文件，不静默重置（M01 已实现） |
| 规则版本变化 | 拒绝加载旧存档（M01 已实现） |
| 服务器时钟回退 | 拒绝结算，返回 `CLOCK_BACKWARDS`（M01 已实现） |
| 重复提交 | 开店天然幂等；解锁/升级靠"目标状态已达成则直接返回成功"实现幂等 |
| 数值溢出 | 触及安全整数上限时返回 `NUMERIC_LIMIT` 且不写入部分结果（M01 已实现） |

## B7 风险与对策

| 风险 | 影响 | 对策 |
| --- | --- | --- |
| 主包体积超限 | 无法提审或首屏加载慢 | 美术走分包 + 压缩，UI 合图集，立绘按需加载；体积上限动手前核对官方文档 |
| 好友排行授权受限 | 排行榜做不出来 | 排在最后做，动手前核对开放数据域文档；准备"只显示自己分数"的降级方案 |
| 素材全是 JPG 假透明 | 无法直接进引擎 | 统一走抠图流水线转透明 PNG，作为独立任务先做 |
| 缺设计图的页面被抢跑 | 返工 | 布局/经营/好友三页在补图前不动工 |
| 数值手感受质疑 | 中期大改 | 数值全部走配置；改配置不改代码 |
| 存档校验强度下降 | 存档被改不容易发现 | 采用分段强校验（方案 A），保留 M01 的自证基线 |
| 上线时忘记关掉本地开发令牌 | 安全漏洞 | 把"关闭本地开发令牌与仅本机限制"列进上线检查清单（《开发规划文档》M09） |
